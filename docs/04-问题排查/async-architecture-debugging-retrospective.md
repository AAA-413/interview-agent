# 异步架构联调排查复盘

> 文档日期：2026-04-17
> 适用范围：本地启动、前后端联调、异步任务链路验证、接口调试排障

---

## 一、这次排查的目标

本轮排查的目标不是单纯“把服务跑起来”，而是验证异步架构一致性优化是否真正落地，重点确认两条长耗时链路：

1. 简历上传后是否改为“接口快速返回 + 后台异步分析”
2. 模拟面试完成后是否改为“答题结束即入队 + 后台异步生成报告”

也就是说，最终想验证的是下面这条完整链路：

```text
前端/接口请求
  -> 后端落库
  -> 状态进入 PENDING
  -> Redis Stream 入队
  -> FastAPI 进程内 worker 消费
  -> 调用 AI 能力执行分析/评估
  -> 状态推进到 COMPLETED 或 FAILED
  -> 前端轮询展示最终结果
```

---

## 二、排查前的代码背景

在开始联调前，异步架构已经完成了一轮代码改造，核心变更包括：

- 简历分析从同步 AI 调用改回 Redis Stream 异步任务
- 面试评估补齐了 producer + worker handler + 状态更新闭环
- `app/main.py` 在 FastAPI lifespan 中启动后台 worker
- 前端页面增加了对 `PENDING / PROCESSING / COMPLETED / FAILED` 的状态展示和轮询逻辑
- report 接口语义调整为：
  - 未完成：不允许看报告
  - 生成中：返回“报告生成中”
  - 失败：返回失败信息
  - 完成：返回最终报告

因此，这次排查的重点已经从“改代码”转移成“验证运行时行为是否符合预期”。

## 三、实际排查过程

### 3.1 第一步：确认服务能否启动

#### 问题 1：后端启动失败，缺少 `uvicorn`

启动命令最初执行后，报错是：

```text
No module named uvicorn
```

#### 分析

这说明不是业务代码错误，而是当前 Python 环境缺少运行时依赖。

#### 处理方式

- 先检查 `pyproject.toml`
- 确认项目依赖中确实声明了 `uvicorn[standard]`
- 安装缺失依赖后重新启动

#### 结论

这一步说明：
- 项目依赖声明是有的
- 问题发生在本地环境，而不是仓库代码本身

---

### 3.2 第二步：修正启动目录问题

#### 问题 2：后端再次启动失败，提示找不到 `app`

报错大意：

```text
ModuleNotFoundError: No module named 'app'
```

#### 分析

这是典型的启动目录错误。`python -m uvicorn app.main:app` 依赖当前工作目录就在项目根目录，否则 Python 无法把 `app` 识别为顶层包。

#### 处理方式

把启动位置切到：

```text
D:\work\xiaofuge\111\python
```

再执行启动命令。

#### 结论

这一步确认：
- 代码模块路径没有问题
- 是命令执行位置不对导致的导入失败

---

### 3.3 第三步：识别 shell 环境差异

#### 问题 3：使用了 Windows `cd /d` 语法，但当前实际运行在 bash 环境

报错：

```text
/usr/bin/bash: line 1: cd: too many arguments
```

#### 分析

`cd /d` 是 cmd 的用法，不是 bash 的用法。说明当前虽然路径是 Windows 风格，但命令执行环境实际是 bash。

#### 处理方式

改成 bash 可接受的形式，例如：

```bash
cd "D:\work\xiaofuge\111\python" && python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

#### 结论

这一步的经验很重要：
- **不要只看路径像 Windows，就默认命令解释器也是 cmd**
- 在混合环境里，优先判断当前 shell 是 bash、powershell 还是 cmd，再写启动命令

---

### 3.4 第四步：确认后端健康检查通过

当启动命令修正后，健康检查接口返回：

{"status":"UP","service":"AI Interview Platform"}

#### 结论

这一步至少证明：
- FastAPI 已经成功启动

- 基础服务没有在启动阶段直接崩掉
- 可以继续做真实接口联调

### 3.5 第五步：启动前端并确认可访问

这说明：

## 四、简历链路联调过程

### 4.1 上传简历测试

使用测试简历文件调用上传接口后，接口成功返回，并且返回数据里的状态是：

```text
analyze_status = PENDING
```

#### 这个结果为什么重要

它说明上传接口已经不再同步等待 AI 分析完成，而是：

1. 先完成文件校验、存储、文本解析、落库
2. 把分析任务投递到异步链路
3. 立刻把结果返回给调用方

这正是本次异步架构优化最核心的目标之一。

#### 阶段性结论

简历链路已经至少验证了下面这半段：

```text
上传请求 -> 落库 -> 状态 PENDING -> 接口快速返回
```

但还没有完全验证后半段：

```text
worker 消费 -> AI 分析 -> 状态 COMPLETED/FAILED
```

### 4.2 继续查询简历详情

再次查询简历详情时，状态仍然是：

```text
PENDING
```

#### 这里不能立刻下结论说“代码有 bug”

因为可能性至少有三类：

1. worker 还没有真正开始消费
2. worker 已消费，但 AI 调用还没完成
3. worker 链路有异常，任务卡在未推进状态

#### 正确判断方式

当看到任务停在 `PENDING` 时，不应该只凭状态猜，而应该继续检查：

- worker 启动日志是否出现
- Redis Stream 是否存在未消费消息
- AI 调用是否报错
- 数据库状态是否有更新失败

#### 经验

- **异步链路的问题不能只看接口返回，要看“状态是否推进”**
- `PENDING` 只是说明“成功入队或准备入队”，不代表“消费成功”

## 六、答题接口排查过程

### 6.1 第一次失败：内联 JSON 请求体解析失败

在命令行里直接用 curl 提交带中文长文本的 JSON 时，后端返回：

```text
There was an error parsing the body
```

#### 根因分析

这类问题通常不是后端 schema 错误，而是 shell 层把 JSON 破坏了。常见原因：

- 引号转义不正确
- 中文内容和双引号嵌套导致字符串提前截断
- shell 对特殊字符做了额外处理

#### 经验

- **长 JSON、中文文本、多行文本，不要优先用 curl 内联 `-d '{...}'`**
- 在联调场景中，最稳妥的方式是把请求体写到文件里，再用 `-d @file.json`

---

### 6.2 第二次失败：误把错误的 JSON 文件发给了 `/answers` 接口

后面又误把 `test_body.json` 发给了答题接口，而这个文件内容其实是：

```json
{"question_count":2}
```

于是后端报了字段校验错误，缺少：

- `question_index`
- `answer`

#### 根因分析

这一次不是后端 bug，也不是接口设计错了，而是联调时把“创建 session 的请求体”和“提交 answer 的请求体”混用了。

#### 经验

联调时要避免把不同接口的测试数据复用到一起。最简单的办法：

- 一个接口一份独立 JSON 文件
- 文件名直接体现接口语义
- 不要用 `test_body.json` 这种过于泛化的名字

---

### 6.3 修正方式：为每道题分别准备标准答案 JSON 文件

为了规避 shell 转义问题，并保证结构正确，后续将答案拆成了 4 个单独文件：

- `tmp-answer-0.json`
- `tmp-answer-1.json`
- `tmp-answer-2.json`
- `tmp-answer-3.json`

每个文件都包含标准结构：

```json
{
  "question_index": 0,
  "answer": "..."
}
```

#### 这样做的好处

1. 彻底绕开 curl 内联 JSON 的转义问题
2. 每次请求的数据结构一目了然
3. 哪一题提交失败，定位更直接
4. 这些文件本身也能作为后续复盘样例

#### 经验总结

在接口联调中，**测试数据文件化** 是一个很值得养成的习惯，尤其是：

- 请求体较长
- 有中文
- 要重复调用同一接口
- 需要留痕复盘

## 七、最终定位出的真实故障与修复

在继续联调后，真正影响本轮异步链路稳定性的，不再是“接口是否可用”，而是两个更底层、更隐蔽的运行时问题。

### 7.1 Redis Stream worker 假性超时

#### 现象

worker 启动后会反复打印类似错误：

```text
redis.exceptions.TimeoutError: Timeout reading from localhost:6379
```

同时表现为：

- 简历分析任务长时间停在 `PENDING`
- 面试评估任务长时间停在 `PENDING`
- 看起来像“worker 已启动但没有消费”

#### 根因

问题不在业务 handler，而在 Redis 客户端配置与阻塞式 `XREAD` 的超时策略冲突：

- `app/infrastructure/redis/redis_service.py` 中 Redis 客户端曾使用过短的 `socket_timeout`
- `app/infrastructure/redis/stream_worker.py` 中 worker 使用 `xread(..., block=5000)` 做阻塞读取
- 两者时间边界过近时，原本合法的阻塞等待会被客户端误判为读超时

这会造成一种很迷惑的现象：

```text
消息其实还没坏，worker 其实也没退出，但消费循环不断报超时、退避、重试
```

#### 修复方式

已做的修复包括：

- 提高 Redis 客户端 `socket_timeout`
- 保留 `socket_connect_timeout` 仅用于连接建立阶段
- 在 `stream_worker.py` 中把读取超时作为明确分支处理，减少误判与日志噪音

#### 修复后验证结果

修复后重新联调可确认：

- 简历异步分析链路可以从 `PENDING` 推进到完成态
- 面试评估链路也可以被 worker 正常消费
- 问题根因确定是 **Redis 阻塞读超时冲突**，不是 producer、handler、落库逻辑整体失效

---

### 7.2 面试 report 接口的 `json` 导入缺失

#### 现象

当面试评估已经完成后：

- `/details` 能返回完整评估内容
- `/report` 却返回 500

报错核心信息为：

```text
name 'json' is not defined
```

#### 根因

`app/modules/interview/session_service.py` 中 `_build_report_dto()` 会解析：

- `strengths_json`
- `improvements_json`
- `reference_answers_json`

但文件顶部缺少：

```python
import json
```

因此 worker 实际已经把评估结果写进数据库，但 report 接口在 DTO 组装阶段失败了。

#### 修复方式

已补充：

```python
import json
```

并重新编译相关文件确认语法通过。

#### 修复后验证结果

在真正释放 8000 端口、关闭旧后端进程并重新启动后，再访问：

```text
GET /api/interview/sessions/9ab21ec445694fe5/report
```

日志确认返回：

```text
200 OK
```

这说明：

- 面试评估后台执行已成功
- report 接口已恢复正常
- 之前报错属于 **已生成数据但接口组装失败**，而不是异步评估本身失败

### 7.3 一个被顺手修掉的可观测性问题

这类包装会严重干扰定位，因此后续已调整异常透传策略，并补充了更清晰的异常处理分层。

## 九、适合以后复用的排查方法论

以后再碰到类似“项目跑起来了，但异步链路不确定是否真的生效”的情况，可以按下面顺序排查：

### 9.1 先确认基础运行环境

顺序建议：

1. 依赖是否安装完整
2. 启动目录是否正确
3. 服务是否真的启动成功
4. 健康检查是否通过

### 9.2 再验证同步入口是否正常

例如：

- 上传接口是否返回成功
- 创建会话接口是否返回成功
- 数据是否真正写入数据库

### 9.3 再验证异步入口是否生效

关键观察点：

- 状态是否进入 `PENDING`
- 是否有 Redis Stream 消息
- 是否有 worker 启动日志

### 9.4 最后验证异步任务是否闭环

关键观察点：

- 状态是否从 `PENDING` 推进到 `PROCESSING`
- 最终是否进入 `COMPLETED` 或 `FAILED`
- 错误信息是否可见
- 前端是否正确停止轮询

### 9.5 调试请求时优先文件化测试数据

建议：

- 创建接口：一个 JSON 文件
- 更新接口：一个 JSON 文件
- 每道题或每种 case 一个单独文件

这样可以显著减少“到底是后端问题还是命令写错了”的时间浪费。

## 十、这次最值得记住的经验

### 经验 1：异步改造是否成功，不能只看接口有没有返回

真正要看的是：

- 是否快速返回
- 是否进入异步状态
- 状态能否被后台任务推进
- 前端是否能正确感知状态变化

### 经验 2：联调失败，优先区分“代码问题”和“操作问题”

这次很多失败其实都不是业务代码问题，而是：

- 环境没装依赖
- 启动目录错了
- shell 命令写法错了
- 请求体文件用错了

如果一上来就怀疑业务代码，排查会跑偏。

### 经验 3：异步系统排查一定要分层

推荐分成这几层看：

```text
启动层
-> 接口层
-> 入队层
-> 消费层
-> AI 执行层
-> 状态落库层
-> 前端展示层
```

不要把“任务没完成”统称为一个问题，否则很难快速定位。

### 经验 4：保留测试样例本身就是复盘资产

像这次生成的：

- 测试简历文件
- 创建 session 的请求体
- 每题答案 JSON 文件

这些都应该保留下来。以后回归测试时，直接复用，比重新手写请求可靠得多。

1. **个人复盘**：回顾一次真实联调里“代码问题”和“操作问题”是怎么区分开的
2. **新人接手**：快速理解这个项目的异步链路应该怎么验证
3. **回归测试**：以后再改 resume/interview 异步逻辑时，可以把这里的步骤当成检查清单
