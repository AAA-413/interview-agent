# 智能面试 Agent 平台 — 面试话术

## 一、项目介绍

### 30 秒版（电梯演讲）

> 我做了一个智能面试 Agent 平台，基于 FastAPI + React + LangChain。核心功能三个：简历上传后 AI 自动五维度评分，基于简历和技能方向的模拟面试（支持实时追问），以及 RAG 知识库问答（Query Rewrite + pgvector 向量检索 + 知识图谱二跳遍历混合检索 + CrossEncoder 重排序）。最有特色的是智能下载功能——用户说"我想学 FastAPI"，系统自动规划、搜索、抓取、清洗、质检、入库，全程约 11 次 LLM 调用，支持选择性重试。后端用 Redis Stream 消费者组做异步任务队列。

### 2 分钟版（技术面试开场）

> 这个项目是一个 AI 驱动的面试准备平台，后端 FastAPI + SQLAlchemy 2.0 异步架构，前端 React + TypeScript + Vite + Tailwind CSS，数据库用 PostgreSQL + pgvector 扩展，缓存和消息队列用 Redis。

> 项目有五大模块：
> 1. **用户认证**：JWT + bcrypt，全局中间件做 token 解析，路由层通过 FastAPI Depends 注入用户 ID，实现了用户级数据隔离。
> 2. **简历管理**：支持 PDF/DOCX/TXT/MD 上传，PyMuPDF 解析文本，SHA-256 哈希去重。后台通过 Redis Stream 异步调用 LLM 做五维度评分（项目经验、技能匹配、内容质量、结构清晰度、表达能力），同时提取结构化简历画像（项目列表、技术栈、经验等级），后续被面试模块复用。
> 3. **模拟面试**：用户选面试方向（10+ 方向，如 Java 后端、AI Agent 等），系统根据简历和技能方向并行生成个性化问题（`asyncio.gather`，出题时间减半）。用户作答后实时追问（最多 2 次），全部作答后异步评估——知识题对比参考答案+关键点逐点评估，项目题四维度打分（真实性、技术深度、思考深度、表达），最终生成面试报告。
> 4. **知识库 + RAG**：文档上传后异步索引（语义切分 → Embedding → pgvector 存储）+ 异步知识图谱抽取（LLM 从文档提取实体-关系三元组，存入 PostgreSQL 三元组表）。问答时先做 Query Rewrite（支持多轮对话上下文改写），然后多通道并行检索——pgvector 向量检索 + 知识图谱二跳遍历，结果合并去重后 CrossEncoder（BAAI/bge-reranker-base）本地重排到最终 top_k，最后 LLM 生成带引用标注的回答，SSE 流式输出。
> 5. **智能下载（Agent 编排）**：最有技术含量的部分。两阶段设计——阶段 1 PlanningAgent 分析意图生成下载计划（6 种任务类型），用户确认后阶段 2 执行。执行时支持动态任务扩展（GitHub 搜索结果自动追加抓取子任务），QualityAgent 两阶段质检（Phase A 规则逐任务评估 + Phase B LLM 整体评估），选择性重试只重试失败任务（成本从 O(n) 降到 O(失败数)），最后 SummaryAgent 精炼文档自动入库。

> 架构上，我做了几个关键决策：用 Redis Stream 而不是 Celery，因为轻量且够用；用 pgvector 而不是独立的向量数据库，因为减少运维复杂度；用 LangChain 的 Structured Output 而不是手写 prompt 解析，因为 JSON schema 约束更可靠。

### 5 分钟版（深入技术细节）

在 2 分钟版基础上，补充以下内容：

> **异步任务架构**：我用 Redis Stream 的消费者组模式（`xreadgroup` + `xack`）实现了轻量级任务队列。抽象了 `StreamTaskProducer`（生产者）和 `StreamTaskHandler`（处理器基类）两个基类，三个 Worker（简历分析、面试评估、知识库索引）各自继承实现。每个 Worker 有唯一消费者名（`name + uuid`），支持水平扩展。每个任务有 5 分钟超时保护（`asyncio.wait_for`），超时自动回滚事务并标记 FAILED。应用启动时在 lifespan 中创建 Worker 任务，关闭时优雅停止（`worker.stop()` + `task.cancel()`）。

> **RAG 检索链路**：一次完整问答 4 次 API 调用——Query Rewrite 1 次 LLM + Embedding 1 次 + CrossEncoder 本地推理 1 次 + 生成回答 1 次 LLM，图谱检索额外 1 次 LLM 做实体提取。Embedding 采用三级降级：Zhipu Embedding-3（2048 维截断到 1536）→ DashScope → SHA-256 哈希向量。文本切分按内容类型差异化——普通文本 900 字/120 重叠，代码块 1200/150（保持完整性），表格 600/50（保持结构）。多通道检索架构：`MultiChannelRetrievalEngine` 并行执行 `VectorSearchChannel`（pgvector cosine_distance）和 `GraphSearchChannel`（图谱二跳遍历），结果合并去重后 CrossEncoder 统一重排序。图谱检索流程：LLM 从问题提取实体 → 二跳遍历三元组 → 直接命中 0.85 分、间接关联 0.65 分。

> **模拟面试引擎**：出题阶段 `asyncio.gather` 并行生成简历题（60%）和方向题（40%），降级策略：简历题失败则全出方向题，全失败则用预设通用题。追问机制：每次回答后 1 次 LLM 判断是否追问，追问时 1 次 LLM 生成追问问题，每道题最多 3 次 LLM 调用。评估用 `asyncio.Semaphore(3)` 控制并发，知识题和项目题分开评估（评估维度不同），全部评估完后 1 次 LLM 生成整体总结。

> **Agent 编排框架**：我设计了一个链式 Agent 架构。`BaseAgent` 抽象类定义了 `get_next()` 方法实现责任链模式，`AgentChain` 负责遍历执行。`AgentFactory` 做依赖注入，`CostController` 跟踪每个 Agent 的 token 消耗并控制预算。

> **数据安全**：所有业务表加了 `user_id` 外键，查询都带用户过滤，解决了 OWASP Top 10 中的 IDOR 问题。JWT token 通过全局中间件解析，存入 `request.state`，路由层通过依赖注入获取。文件上传做了文件名清理（防路径遍历）和 PDF 魔术字节检测。

## 二、技术挑战与解决方案

### 挑战 1：LLM 调用超时和限流

**问题**：LLM 调用不稳定，有时超时（300s+），有时触发限流（429），导致用户体验差。

**解决**：
- 在 `MonitoredChatModel` 中用装饰器模式包装 `ainvoke`，统一捕获 `APITimeoutError` 和 `RateLimitError`，转换为业务异常
- 全局信号量 `asyncio.Semaphore(10)` 限制 LLM 并发调用数，防止触发 provider 限流
- 超时设 300s（智能下载需要长时间），重试 2 次
- 异步任务加了 `asyncio.wait_for` 5 分钟超时兜底，超时后自动回滚事务并标记 FAILED
- 前端轮询加最大次数限制，超时显示友好提示

**面试话术**：
> "LLM 调用的不稳定性是最大的工程挑战。我用装饰器模式在 `ainvoke` 层统一做异常转换，把 OpenAI SDK 的 `APITimeoutError` 转成用户友好的'AI 服务响应超时，请稍后重试'。同时用全局信号量限制并发数为 10，避免同时发起太多请求触发限流。后台任务加了双层超时——LLM SDK 自身的 300s 超时，加上 `asyncio.wait_for` 的 5 分钟任务级超时，超时后自动回滚事务保证数据一致性。"

### 挑战 2：Embedding 维度不一致

**问题**：Zhipu Embedding-3 输出 2048 维，但 pgvector 列定义是 1536 维；DashScope API 不稳定时需要降级方案。

**解决**：
- Zhipu 2048 维直接截断到 1536 维（前 1536 维包含主要语义信息）
- DashScope 作为备选 provider
- 终极降级：SHA-256 多轮哈希填充到 1536 维——对 `hash + round_index` 重复哈希，拼接直到足够长度，最后 L2 归一化

**面试话术**：
> "Embedding 方案做了三级降级。主方案用 Zhipu Embedding-3，2048 维截断到 1536 维，截断损失很小。如果 Zhipu 不可用，降级到 DashScope text-embedding-v2。如果所有 Embedding API 都挂了，用 SHA-256 多轮哈希生成确定性伪向量——每轮对 `原始hash + 轮次索引` 再哈希，保证不同轮次输出不同，最后 L2 归一化。语义质量差但保证系统不崩溃。"

### 挑战 3：智能下载的选择性重试

**问题**：原来 10 个下载任务中 1 个失败，就要清空全部结果重新下载 10 个，成本高。

**解决**：
- QualityAgent 两阶段评估：Phase A 用规则逐任务检查（内容实质性 + 主题相关性，0 次 LLM），返回 `failed_task_indices`；Phase B 用 LLM 整体评估（覆盖度 + 多样性），输出 `expanded_keywords` 供重试使用
- 选择性重试：只重试 `failed_task_indices` 中的任务，`successful_results` 字典跨轮次持久化
- 宽松 relevance 评分：三层兜底（无关键词→60 分默认通过；0 命中→25 分标记失败；有命中→max(30, 正常计算)）
- 重试时合并 Phase B 输出的 `expanded_keywords`（同义词/相关词），原来 0 命中的内容可能因扩展词命中而通过

**面试话术**：
> "智能下载的质量检查是两阶段架构。Phase A 用规则做快速筛选——检查内容长度、模板检测、关键词匹配，0 次 LLM 调用就能过滤掉明显不合格的任务。Phase B 才调 LLM 评估整体覆盖度和多样性。选择性重试是关键优化——Phase A 返回 `failed_task_indices`，重试时只执行失败任务，成功结果跨轮次保留。下载成本从 O(n) 降到 O(失败数)。同时 Phase B 输出 `expanded_keywords`，重试时合并到关键词列表，提高通过率。"

### 挑战 4：Redis Stream 消费者组的 Pending 队列

**问题**：从 `xread` 广播模式迁移到 `xreadgroup` 消费者组后，消费者崩溃会导致消息卡在 Pending 队列。

**解决**：当前实现用 `xreadgroup` + `xack` 确认机制。Worker 有唯一消费者名（`name + uuid`），处理成功后才 ACK。每个任务 5 分钟超时保护，超时后开新连接更新状态为 FAILED。未来可以加 `XPENDING` + `XCLAIM` 做死信队列重试。

**面试话术**：
> "Redis Stream 的消费者组有个坑——如果消费者拿到消息后崩溃，消息会卡在 Pending 队列。我的解决方案是处理成功后才 `xack`，并且每个消费者用 UUID 命名避免冲突。超时用 `asyncio.wait_for` 5 分钟兜底，超时后开新连接更新状态为 FAILED（因为原事务已回滚）。目前的实现是'至少一次'语义，如果要做到'恰好一次'，需要在 handler 层做幂等性保证。"

### 挑战 5：SSE 流式输出的实现

**问题**：最初的"流式"是先等 LLM 生成完整回答，再分块推送给前端，用户等待时间长。

**解决**：改用 LangChain `astream()` 方法，拿到 `AsyncIterator`，逐 token 写入 SSE。前端用 `fetch` + `ReadableStream` 的 reader 逐 chunk 解析。SSE 事件包含 meta（session_id）、references（引用来源）、chunk（token）、done（完整回答）。

**面试话术**：
> "真正的流式输出和伪流式差别很大。伪流式用户要等整个 LLM 回答生成完（可能 30 秒），才能看到第一个字。改用 `astream()` 后，第一个 token 出来就推给前端，用户 1-2 秒就能看到反馈。SSE 事件分四种类型——meta 推送会话信息，references 推送引用来源（[1][2] 标注），chunk 逐 token 推送内容，done 推送完整回答用于校验。技术关键是 SSE 的 `Content-Type: text/event-stream` + `Cache-Control: no-cache`，以及 Nginx 要关闭 `proxy_buffering`。"

### 挑战 6：知识图谱与向量检索的混合检索

**问题**：纯向量检索对关系型问题（"Redis 和 MySQL 的区别"、"学 Spring Boot 要先学什么"）效果差，答案分散在不同 chunk 中，向量相似度无法捕捉结构化关系。

**解决**：
- 知识库入库时异步调用 LLM 抽取实体-关系三元组（7 种实体类型 + 9 种关系类型），存入 PostgreSQL 三元组表（`kg_entities` + `kg_triples`）
- 问答时图谱检索作为第二个通道接入 `MultiChannelRetrievalEngine`，和向量检索 `asyncio.gather` 并行执行
- 图谱检索流程：LLM 从问题提取实体（最多 5 个）→ 二跳遍历（`query_two_hop`）→ 三元组转为引用片段（直接命中 0.85 分，间接关联 0.65 分）
- 结果合并去重后交给 CrossEncoder 重排序，统一进入生成阶段

**面试话术**：
> "向量检索对描述性问题效果好，但对关系型问题有盲区。比如'Redis 和 Memcached 的区别'，向量检索可能只返回提到 Redis 的 chunk，漏掉 Memcached。知识图谱用三元组显式存储实体关系，图谱检索做二跳遍历能发现间接关联。两个通道并行执行，结果合并后 CrossEncoder 统一重排序。架构上用 `SearchChannel` 抽象接口，新增检索通道只需要实现 `search()` 方法，不影响现有流程。"

### 挑战 7：模拟面试的追问与分类评估

**问题**：知识题和项目题混在一起评估导致 LLM 评估标准混乱，追问机制需要精细的 LLM 决策。

**解决**：
- 追问决策：每次回答后 LLM 判断 `shouldFollowUp`，返回追问问题、参考答案、关键点和决策理由。最多追问 2 次，追问继承原题类型（知识/项目）
- 分类评估：知识题对比参考答案 + 关键点逐点评估（coveredPoints / missedPoints / errors）；项目题四维度打分（真实性、技术深度、思考深度、表达）
- 并发控制：`asyncio.Semaphore(3)` 限制评估并发数
- 总结：全部评估完后 LLM 生成整体反馈 + 优势 + 改进建议，失败时降级到批次聚合

**面试话术**：
> "模拟面试的评估分知识题和项目题两条路径。知识题有标准答案和关键点，评估重点是'答对了多少、遗漏了什么、有什么错误'；项目题没有标准答案，评估重点是'是否真实参与、技术深度如何、思考是否有深度、表达是否清晰'，用四维度打分。追问是实时的——每次回答后 LLM 判断是否需要追问，追问时生成带有参考答案和关键点的新问题，最多追问 2 次。全部评估用信号量控制并发，避免 API 限流。"

## 三、架构决策与理由

### 为什么用 Redis Stream 而不是 Celery？

| 维度 | Redis Stream | Celery |
|------|-------------|--------|
| 运维复杂度 | 低（只需 Redis） | 高（Broker + Result Store + Beat） |
| 消息可靠性 | 消费者组 + ACK | 依赖 Broker 配置 |
| 水平扩展 | 添加消费者即可 | 需要 Worker 进程管理 |
| 适用规模 | 中小规模（本项目） | 大规模分布式 |
| 学习成本 | 低 | 高 |

> "这个项目是 4 核 4G 的服务器，任务量不大。Redis Stream 的消费者组完全够用，省去了 Celery 的 Broker + Result Store 配置。而且 Redis 同时承担缓存（计划存储、取消标记）和消息队列，减少了一个组件的运维。"

### 为什么用 pgvector 而不是 Milvus/Weaviate？

> "项目本身已经用了 PostgreSQL，pgvector 是一个扩展而不是独立服务，不需要额外部署和运维。对于我的数据量（几千条文档 chunk），pgvector 的 cosine_distance 性能完全够用。如果数据量到百万级，我会考虑 Milvus。"

### 为什么用 CrossEncoder 而不是纯向量检索？

> "向量检索用的是 Bi-Encoder 架构，query 和 document 独立编码，速度快但无法捕捉 token 级别的交互。CrossEncoder 把 query 和候选片段拼接后联合编码，精度更高，但速度慢（O(n)）。所以采用两阶段方案——向量检索召回 2 倍候选，CrossEncoder 精排到最终 top_k，在速度和精度之间取得平衡。CrossEncoder 用本地模型（BAAI/bge-reranker-base），一次 forward pass 处理所有候选，延迟百毫秒级。"

### 为什么用 LangChain Structured Output？

> "LLM 返回的 JSON 经常格式不对——少一个字段、多一个逗号、类型不对。LangChain 的 Structured Output 用 JSON Schema 约束输出格式，PydanticOutputParser 自动做校验，失败时附加 repair prompt 和上次错误信息重试。比手写正则解析可靠得多。"

### 为什么用 FastAPI 的中间件而不是装饰器做认证？

> "全局中间件的好处是'默认安全'——所有路由默认需要认证，只有白名单路径（登录、注册、健康检查）放行。这样不会因为忘记加装饰器而暴露接口。中间件只做 token 解析，用户信息存 `request.state`，路由层通过 `Depends(get_current_user_id)` 获取，职责分离清晰。"

### 为什么用向量+图谱混合检索而不是纯向量？

> 向量检索用 Bi-Encoder 把 query 和 document 分别编码成向量，通过余弦相似度匹配。它擅长"这段话大概在说什么"的语义匹配，但无法捕捉结构化关系。比如"Redis 解决了什么问题"，答案是"缓存穿透、缓存击穿、缓存雪崩"，这些是显式的"解决"关系，分散在不同 chunk 中。向量检索可能只返回提到 Redis 的 chunk，但不一定提到具体解决了什么问题。知识图谱用三元组（Redis 解决 缓存穿透）显式存储这种关系，二跳遍历能发现间接关联。两个通道并行执行、结果互补，CrossEncoder 统一重排序保证最终质量。

### 为什么用两阶段设计做智能下载？

> "智能下载的执行时间长（可能几分钟），如果直接执行，用户没法干预。两阶段设计让用户先看到下载计划（包含哪些任务、搜索什么关键词），确认后再执行。计划存在 Redis 中（TTL 1 小时），用户可以取消（Redis flag 标记）。这比'黑盒执行'的用户体验好很多。"

## 四、优化过程（可以主动提到）

### 阶段一：安全加固
- 修复 IDOR 漏洞：所有业务表加 `user_id` 外键，查询带用户过滤
- 输入校验：`question_count` 加范围限制，`answer` 加长度上限
- 文件上传安全：文件名清理 + PDF 魔术字节检测
- JWT 认证链路优化：中间件只解析 token，路由层通过 Depends 获取用户

### 阶段二：用户体验
- SSE 真流式输出：`astream()` 替代伪流式
- 异步任务超时兜底：`asyncio.wait_for` 5 分钟超时
- 错误码映射：`RESUME_NOT_FOUND` 返回 404 而非 500
- 前端体验：移除默认账号显示，401 路由跳转

### 阶段三：架构优化
- Redis Stream 消费者组：`xreadgroup` + `xack` 替代 `xread` 广播
- LLM 监控包装器：装饰器模式记录 token 消耗和调用时长，全局信号量限制并发
- Embedding 三级降级：Zhipu → DashScope → Hash 向量
- 追问机制：从无追问到 LLM 决策追问（最多 2 次）
- 评估分离：知识题和项目题分开评估，各用不同评分体系

**面试话术**：
> "项目不是一步到位的。第一版有很多安全问题——没有用户隔离、输入没校验、文件上传没检查。我分三个阶段系统性地优化：安全 → 体验 → 架构。每个阶段都有明确的目标和可衡量的结果。这种迭代优化的能力比一次性写出完美代码更重要。"

## 六、高频面试问题

### Q: 项目用了什么技术栈？

> 后端 FastAPI + SQLAlchemy 2.0 异步 + PostgreSQL + pgvector + Redis。前端 React + TypeScript + Vite + Tailwind CSS + AntV G6（知识图谱可视化）。AI 部分用 LangChain + DeepSeek（deepseek-chat）。Embedding 用 Zhipu Embedding-3。部署用 Docker Compose + Nginx 反向代理。

### Q: 项目的难点在哪里？

> 三个难点：第一，LLM 调用的不确定性——超时、限流、返回格式不稳定，需要做异常处理、重试、降级、信号量限流。第二，Agent 编排的复杂性——多 Agent 协作需要设计好职责边界和数据流转，质量检查要支持选择性重试。第三，RAG 的质量——从语义切分、Embedding 降级、Query Rewrite 到 CrossEncoder 重排序，每一步都影响最终回答质量。

### Q: 如果重新设计，你会怎么改？

> 三个方面：第一，任务队列会考虑用 Redis + 自研调度器，而不是直接用 Stream，因为 Stream 的 Pending 队列重试机制不够完善。第二，Agent 通信会用事件驱动而不是直接调用，解耦更彻底。第三，前端状态管理会用 Zustand 替代当前的 useState，减少 prop drilling。

### Q: 怎么保证 LLM 返回结果的可靠性？

> 四层保障：1) LangChain Structured Output 用 JSON Schema 约束格式，失败时附加 repair prompt + 错误信息重试；2) 选择性重试（QualityAgent 返回 failed_task_indices，只重试失败任务）；3) 两阶段质检（Phase A 规则评估做快速筛选 0 次 LLM，Phase B LLM 评估做整体判断）；4) 超时控制（`asyncio.wait_for` 防止无限等待，全局信号量防止并发过高）。

### Q: 项目的性能瓶颈在哪？

> 主要瓶颈是 LLM 调用延迟。一次完整的模拟面试（8 题）需要调用 LLM 8+ 次（出题 2 次并行 + 逐题评估 + 整体评估），每次 5-30 秒。优化方向：并行出题（`asyncio.gather` 减半出题时间）、信号量控制评估并发（Semaphore(3)）、缓存常见问题的回答。

### Q: 数据库怎么设计的？

> 核心表：`users`（用户）、`resumes` + `resume_analyses`（简历 + 分析结果）、`interview_sessions` + `interview_answers`（面试会话 + 答题记录）、`knowledge_bases` + `knowledge_chunks`（知识库 + 文档分块 + pgvector 向量）、`knowledge_entities` + `knowledge_triples`（知识图谱实体 + 三元组）。所有业务表通过 `user_id` 外键关联用户，实现数据隔离。向量检索用 pgvector 的 cosine_distance 操作符。

### Q: 怎么部署的？

> Docker Compose 编排 5 个服务：PostgreSQL（pgvector 镜像）、Redis、MinIO（对象存储）、后端（gunicorn + uvicorn workers）、Nginx（前端静态文件 + API 反向代理）。生产环境密钥通过环境变量注入，Redis 和数据库加密码认证，Nginx 配了安全头和 SSE 流式支持。

### Q: 测试怎么做？

> 目前有 pytest + pytest-asyncio 框架（asyncio_mode="auto"）。核心链路测试：简历上传 → 分析 → 查看报告；创建面试 → 出题 → 作答 → 评估 → 查看报告；知识库上传 → 索引 → RAG 问答。LLM 调用在测试中 mock 掉，用固定响应验证流程正确性。`ruff` 做代码规范检查。

### Q: 知识库一开始是向量检索，后面为什么添加知识图谱？

> 一开始我只用 pgvector 做向量检索——用户问题经过 Embedding 后，和文档 chunk 做 cosine_distance 比较，召回最相似的片段。这对"描述性"问题效果不错，比如"FastAPI 怎么配置中间件"，因为答案就在某个 chunk 里，向量相似度能匹配到。
>
> 但有一种问题向量检索搞不定：**关系型问题**。比如用户问"Redis 和 MySQL 的区别"、"学 Spring Boot 之前要先学什么"、"Redis 解决了哪些问题"。这类问题的答案不是一个连续的文本片段，而是分散在不同文档中的实体关系——Redis 是缓存技术、MySQL 是关系数据库、Spring Boot 前置知识是 Spring Core、Redis 解决缓存穿透。这些关系信息在向量空间里没有明确的结构化表达，chunk 里可能只提到了一嘴，检索不出来或者排在很后面。
>
> 所以我加了知识图谱，用 PostgreSQL 三元组表（`kg_entities` + `kg_triples`）存储实体-关系-实体结构。知识库文档入库时，异步调用 LLM 从文本中抽取实体和关系，定义了 7 种实体类型（技术、概念、工具、框架、公司、人、面试题）和 9 种关系类型（属于、使用、前置知识、常配合、包含、解决、对比、优缺点、适用场景）。抽取按 2000 字分段进行，结果去重后存入三元组表，实体有 `mention_count` 记录出现频次。
>
> 问答时，把图谱检索作为第二个通道接入多通道检索引擎（`MultiChannelRetrievalEngine`），和向量检索 `asyncio.gather` 并行执行，结果合并去重后交给 CrossEncoder 重排序。图谱检索的流程是：LLM 从问题中提取实体名称（最多 5 个），然后做二跳遍历（`query_two_hop`）——先找实体的直接关系，再找邻居的关系，能发现间接关联。相关度打分规则：直接命中的三元组 0.85 分，间接关联的 0.65 分。

**面试官可能追问：为什么不直接用 Neo4j？**

> 项目已经用了 PostgreSQL，知识图谱的数据量不大（几千个实体、几万个三元组），用两张关系表就能存储，不需要引入额外的图数据库。PostgreSQL 的 JOIN 和索引（`idx_kg_entity_name`、`idx_kg_triple_subject` 等）完全够用。而且知识图谱和业务数据在同一个库，可以做级联删除（`ondelete="CASCADE"`），清理知识库时自动清理关联的三元组。如果数据量到百万级三元组，或者需要复杂的图算法（最短路径、社区检测），我会考虑 Neo4j。

### Q: 你是如何验证知识库检索的准确性的？

> 我从三个层面验证检索质量：
>
> **第一层：CrossEncoder 重排序做精度兜底。** 向量检索和图谱检索各自召回候选后，不是直接取 top_k，而是过一遍 CrossEncoder（BAAI/bge-reranker-base）。CrossEncoder 把 query 和候选片段拼接后联合编码，能捕捉 token 级别的语义交互，比单纯的向量相似度精度高很多。先召回 2 倍候选（`top_k * 2`），CrossEncoder 精排到最终 top_k。这一步是"检索质量的最后一道防线"。
>
> **第二层：引用标注让用户可验证。** 生成的回答用 [1][2] 标注引用来源，前端展示每个引用的标题、内容预览和相关度分数。用户可以直观判断回答是否基于正确的知识片段。如果引用的片段和问题不相关，说明检索有问题。
>
> **第三层：对话历史持久化，支持人工抽检。** 每次问答的 `rewritten_query`、`references`（含 score 和 source_name）、`answer` 都存入 `rag_chats` 表。我可以事后查询某条对话的检索结果，分析是检索阶段出了问题（参考片段不相关）还是生成阶段出了问题（参考片段对了但回答偏离）。
>
> 如果要系统性评估，我的思路是：构造一个标注数据集（问题 + 期望引用的 chunk_id），跑 precision@k 和 recall@k 指标，按通道分别统计向量检索和图谱检索的贡献。当前项目阶段还没做这一步，但架构上支持——多通道检索引擎的 `SearchChannelResult` 返回了 `channel_name` 和 `latency_ms`，可以按通道统计检索效果。

### Q: 添加了知识图谱混合检索，效果提升了多少？

> 老实说，没有做过严格的 A/B 测试来量化提升，但我可以从架构设计角度分析知识图谱解决了什么问题：
>
> **第一，关系型问题的召回率提升。** 纯向量检索对"Redis 和 Memcached 的区别"这类问题效果差——这两个名词的向量表示距离可能很近，但检索到的 chunk 可能只提到了其中一个，或者只是顺带提了一嘴。知识图谱里有显式的三元组（Redis 对比 Memcached），加上各自的描述，能直接返回结构化的关系信息。图谱检索做了二跳遍历（`query_two_hop`），先找 Redis 的直接关系，再找 Redis 邻居的关系，能发现间接关联。
>
> **第二，检索结果的多样性提升。** 向量检索容易"语义坍缩"——top_k 个结果都是同一个话题的不同表述。图谱检索返回的是结构化三元组（subject —[predicate]→ object），信息密度更高，和向量检索的结果互补。多通道引擎 `asyncio.gather` 并行执行两个通道，合并去重后按分数排序。
>
> **第三，可扩展性。** 多通道检索架构（`SearchChannel` 抽象接口 + `MultiChannelRetrievalEngine`）支持随时添加新通道，比如 BM25 关键词检索、SQL 结构化查询。新增通道只需要实现 `search()` 方法并注册到引擎，不影响现有流程。
>
> 如果要量化评估，我会构造一个包含关系型问题的测试集，对比"纯向量检索"和"向量+图谱混合检索"的 precision@4，重点关注关系型问题的召回率差异。
