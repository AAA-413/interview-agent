# 智能面试 Agent 平台 — 面试话术

## 一、项目介绍

### 30 秒版（电梯演讲）

> 我做了一个智能面试 Agent 平台，基于 FastAPI + React + LangChain。核心功能三个：简历上传后 AI 自动评分，基于简历和 JD 的模拟面试，以及 RAG 知识库问答。最有特色的是智能下载功能——用户说"我想学 FastAPI"，系统自动规划、搜索、抓取网页内容，清洗后索引到知识库，全程无人工干预。后端用了 Redis Stream 消费者组做异步任务队列，pgvector 做向量检索。

### 2 分钟版（技术面试开场）

> 这个项目是一个 AI 驱动的面试准备平台，后端 FastAPI + SQLAlchemy 2.0 异步架构，前端 React + TypeScript + Ant Design，数据库用 PostgreSQL + pgvector 扩展，缓存和消息队列用 Redis。

> 项目有五大模块：
> 1. **用户认证**：JWT + bcrypt，全局中间件做 token 解析，路由层通过 FastAPI Depends 注入用户 ID，实现了用户级数据隔离。
> 2. **简历管理**：支持 PDF/DOCX 上传，PyMuPDF 解析文本，后台异步调用 LLM 做简历评分和分析，生成结构化报告。
> 3. **模拟面试**：用户选面试方向（Java 后端、AI Agent 等），系统根据简历和 JD 生成个性化问题，用户作答后 LLM 逐题评估+整体评估，支持追问。
> 4. **知识库 + RAG**：文档上传后自动分块、向量化（DashScope embedding）、存入 pgvector。问答时做相似度检索 + 重排序 + LLM 生成，支持真正的 SSE 流式输出。
> 5. **智能下载（Agent 编排）**：这是最有技术含量的部分。用决策树分析用户意图，PlanningAgent 生成下载计划，ExecutionAgent（Web 抓取 + GitHub 搜索）并行执行，QualityAgent 做两阶段质量检查（Phase A 规则逐任务评估 + Phase B LLM 整体评估），支持选择性重试（只重试失败任务），最后 SummaryAgent 整合输出。整个流程用 Redis Stream 消费者组做异步任务调度。

> 架构上，我做了几个关键决策：用 Redis Stream 而不是 Celery，因为轻量且够用；用 pgvector 而不是独立的向量数据库，因为减少运维复杂度；用 LangChain 的 Structured Output 而不是手写 prompt 解析，因为 JSON schema 约束更可靠。

### 5 分钟版（深入技术细节）

在 2 分钟版基础上，补充以下内容：

> **异步任务架构**：我用 Redis Stream 的消费者组模式（`xreadgroup` + `xack`）实现了轻量级任务队列。每个 Worker 有唯一消费者名，支持水平扩展。消息处理失败不会 ACK，Pending 队列可以重试。相比 Celery，省去了 Broker + Result Store + Beat 三个组件的运维。

> **Agent 编排框架**：我设计了一个链式 Agent 架构。`BaseAgent` 抽象类定义了 `get_next()` 方法实现责任链模式，`AgentChain` 负责遍历执行。`AgentFactory` 做依赖注入，`CostController` 跟踪每个 Agent 的 token 消耗并控制预算。执行策略分三种：顺序、并行（无依赖的子任务）、混合（拓扑排序+依赖感知）。

> **RAG 流式输出**：最初是伪 SSE（先完整生成再分块推送），后来改成了 LangChain `astream()` 真正的 token-by-token 流式。前端用 `fetch` + `ReadableStream` 逐 token 渲染，用户可以实时看到回答生成过程。

> **数据安全**：所有业务表加了 `user_id` 外键，查询都带用户过滤，解决了 OWASP Top 10 中的 IDOR 问题。JWT token 通过全局中间件解析，存入 `request.state`，路由层通过依赖注入获取。文件上传做了文件名清理（防路径遍历）和 PDF 魔术字节检测。

## 二、技术挑战与解决方案

### 挑战 1：LLM 调用超时和限流

**问题**：LLM 调用不稳定，有时超时（300s+），有时触发限流（429），导致用户体验差。

**解决**：
- 在 `LlmProviderRegistry` 中用装饰器模式包装 `ainvoke`，统一捕获 `APITimeoutError` 和 `RateLimitError`，转换为业务异常
- 超时设 300s（智能下载需要长时间），重试 2 次
- 异步任务加了 `asyncio.wait_for` 5 分钟超时兜底，超时后标记任务为 FAILED
- 前端轮询加最大次数限制，超时显示友好提示

**面试话术**：
> "LLM 调用的不稳定性是最大的工程挑战。我用装饰器模式在 `ainvoke` 层统一做异常转换，把 OpenAI SDK 的 `APITimeoutError` 转成用户友好的'AI 服务响应超时，请稍后重试'。后台任务加了双层超时——LLM SDK 自身的 300s 超时，加上 `asyncio.wait_for` 的 5 分钟任务级超时。"

### 挑战 2：Embedding 维度不一致

**问题**：DashScope embedding API 不稳定，降级方案用 SHA-256 哈希生成向量，但维度只有 256，pgvector 列定义是 1536 维，插入失败。

**解决**：用多轮 SHA-256 哈希填充到 1536 维——对 `hash + round_index` 重复哈希，拼接直到足够长度，最后归一化。

**面试话术**：
> "Embedding API 不稳定时需要降级方案。我用多轮 SHA-256 哈希生成伪向量，关键是要填充到和 pgvector 列定义一致的 1536 维。每轮对 `原始hash + 轮次索引` 再哈希，保证不同轮次的输出不同，最后 L2 归一化。这虽然不能保证语义质量，但至少让系统不会崩溃。"

### 挑战 3：Redis Stream 消费者组的 Pending 队列

**问题**：从 `xread` 广播模式迁移到 `xreadgroup` 消费者组后，消费者崩溃会导致消息卡在 Pending 队列。

**解决**：当前实现用 `xreadgroup` + `xack` 确认机制。Worker 有唯一消费者名（`name + uuid`），处理成功后才 ACK。未来可以加 `XPENDING` + `XCLAIM` 做死信队列重试。

**面试话术**：
> "Redis Stream 的消费者组有个坑——如果消费者拿到消息后崩溃，消息会卡在 Pending 队列。我的解决方案是处理成功后才 `xack`，并且每个消费者用 UUID 命名避免冲突。目前的实现是'至少一次'语义，如果要做到'恰好一次'，需要在 handler 层做幂等性保证。"

### 挑战 4：SSE 流式输出的实现

**问题**：最初的"流式"是先等 LLM 生成完整回答，再分块推送给前端，用户等待时间长。

**解决**：改用 LangChain `astream()` 方法，拿到 `AsyncIterator`，逐 token 写入 SSE。前端用 `fetch` + `ReadableStream` 的 reader 逐 chunk 解析。

**面试话术**：
> "真正的流式输出和伪流式差别很大。伪流式用户要等整个 LLM 回答生成完（可能 30 秒），才能看到第一个字。改用 `astream()` 后，第一个 token 出来就推给前端，用户 1-2 秒就能看到反馈。技术关键是 SSE 的 `Content-Type: text/event-stream` + `Cache-Control: no-cache`，以及 Nginx 要关闭 `proxy_buffering`。"

## 三、架构决策与理由

### 为什么用 Redis Stream 而不是 Celery？

| 维度 | Redis Stream | Celery |
|------|-------------|--------|
| 运维复杂度 | 低（只需 Redis） | 高（Broker + Result Store + Beat） |
| 消息可靠性 | 消费者组 + ACK | 依赖 Broker 配置 |
| 水平扩展 | 添加消费者即可 | 需要 Worker 进程管理 |
| 适用规模 | 中小规模（本项目） | 大规模分布式 |
| 学习成本 | 低 | 高 |

> "这个项目是 4 核 4G 的服务器，任务量不大。Redis Stream 的消费者组完全够用，省去了 Celery 的 Broker + Result Store 配置。而且 Redis 同时承担缓存和消息队列，减少了一个组件的运维。"

### 为什么用 pgvector 而不是 Milvus/Weaviate？

> "项目本身已经用了 PostgreSQL，pgvector 是一个扩展而不是独立服务，不需要额外部署和运维。对于我的数据量（几千条文档 chunk），pgvector 的 HNSW 索引性能完全够用。如果数据量到百万级，我会考虑 Milvus。"

### 为什么用 LangChain Structured Output？

> "LLM 返回的 JSON 经常格式不对——少一个字段、多一个逗号、类型不对。LangChain 的 Structured Output 用 JSON Schema 约束输出格式，自动做重试和修复。比手写正则解析可靠得多。"

### 为什么用 FastAPI 的中间件而不是装饰器做认证？

> "全局中间件的好处是'默认安全'——所有路由默认需要认证，只有白名单路径（登录、注册、健康检查）放行。这样不会因为忘记加装饰器而暴露接口。中间件只做 token 解析，用户信息存 `request.state`，路由层通过 `Depends(get_current_user_id)` 获取，职责分离清晰。"

## 四、优化过程（可以主动提到）

### 阶段一：安全加固
- 修复 IDOR 漏洞：所有业务表加 `user_id` 外键，查询带用户过滤
- 输入校验：`question_count` 加范围限制，`answer` 加长度上限
- 文件上传安全：文件名清理 + PDF 魔术字节检测
- JWT 认证链路优化：中间件只解析 token，路由层通过 Depends 获取用户

### 阶段二：用户体验
- SSE 真流式输出：`astream()` 替代伪流式
- 异步任务超时兜底：`asyncio.wait_for` 5 分钟超时
- 错误码映射：`RESUME_NOT_FOUND` 返回 404 而非 500
- 前端体验：移除默认账号显示，401 路由跳转

### 阶段三：架构优化
- Redis Stream 消费者组：`xreadgroup` + `xack` 替代 `xread` 广播
- LLM 监控包装器：装饰器模式记录 token 消耗和调用时长
- Embedding 维度一致性：哈希降级填充到 1536 维
- 消息完整性：修复 system 消息被丢弃的 bug

**面试话术**：
> "项目不是一步到位的。第一版有很多安全问题——没有用户隔离、输入没校验、文件上传没检查。我分三个阶段系统性地优化：安全 → 体验 → 架构。每个阶段都有明确的目标和可衡量的结果。这种迭代优化的能力比一次性写出完美代码更重要。"

## 五、高频面试问题

### Q: 项目用了什么技术栈？

> 后端 FastAPI + SQLAlchemy 2.0 异步 + PostgreSQL + pgvector + Redis。前端 React + TypeScript + Vite + Tailwind CSS。AI 部分用 LangChain + 阿里云百炼（qwen-plus）。部署用 Docker Compose + Nginx 反向代理。

### Q: 项目的难点在哪里？

> 三个难点：第一，LLM 调用的不确定性——超时、限流、返回格式不稳定，需要做异常处理、重试、降级。第二，Agent 编排的复杂性——多 Agent 协作需要设计好职责边界和数据流转。第三，RAG 的质量——从文档分块、embedding 质量、检索策略到重排序，每一步都影响最终回答质量。

### Q: 如果重新设计，你会怎么改？

> 三个方面：第一，任务队列会考虑用 Redis + 自研调度器，而不是直接用 Stream，因为 Stream 的 Pending 队列重试机制不够完善。第二，Agent 通信会用事件驱动而不是直接调用，解耦更彻底。第三，前端状态管理会用 Zustand 替代当前的 useState，减少 prop drilling。

### Q: 怎么保证 LLM 返回结果的可靠性？

> 四层保障：1) LangChain Structured Output 用 JSON Schema 约束格式；2) 重试机制（`max_retries=2`，选择性重试只重试失败任务）；3) 两阶段质检（Phase A 规则评估做快速筛选，Phase B LLM 评估做整体判断，Phase B 失败时降级到规则评估）；4) 超时控制（`asyncio.wait_for` 防止无限等待）。

### Q: 项目的性能瓶颈在哪？

> 主要瓶颈是 LLM 调用延迟。一次完整的模拟面试（8 题）需要调用 LLM 8+ 次（出题、逐题评估、整体评估），每次 5-30 秒。优化方向：并行评估无依赖的题目、缓存常见问题的回答、用更快的模型做初筛。

### Q: 数据库怎么设计的？

> 核心表：`users`（用户）、`resumes`（简历）、`interview_sessions`（面试会话）、`interview_answers`（答题记录）、`knowledge_bases`（知识库）、`knowledge_chunks`（文档分块+向量）。所有业务表通过 `user_id` 外键关联用户，实现数据隔离。向量检索用 pgvector 的 HNSW 索引，`vector_cosine_ops` 做余弦相似度。

### Q: 怎么部署的？

> Docker Compose 编排 5 个服务：PostgreSQL（pgvector 镜像）、Redis、MinIO（对象存储）、后端（gunicorn + uvicorn workers）、Nginx（前端静态文件 + API 反向代理）。生产环境密钥通过环境变量注入，Redis 和数据库加密码认证，Nginx 配了安全头和 SSE 流式支持。

### Q: 测试怎么做？

> 目前有 pytest + pytest-asyncio 框架。核心链路测试：简历上传 → 分析 → 查看报告；创建面试 → 出题 → 作答 → 评估 → 查看报告；知识库上传 → 索引 → RAG 问答。LLM 调用在测试中 mock 掉，用固定响应验证流程正确性。
