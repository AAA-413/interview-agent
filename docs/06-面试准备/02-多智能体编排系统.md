# 多智能体编排系统 — 面试技术细节

## 一、整体架构

```
用户输入
  ↓
SmartDecisionTree（LLM驱动的决策树，1次LLM调用）
  ↓ 选择执行路径: simple / standard / complex（记录用，不影响执行行为）
  ↓
PlanningAgent（任务规划，1次LLM调用）
  ↓ 生成子任务列表 + 执行策略（sequential/parallel/hybrid）
  ↓ 设置 requires_quality_check（simple任务跳过质检）
  ↓
ExecutionAgent(s)（执行子任务，策略模式 — 6个具体子类）
  ├─ sequential: 顺序执行（orchestrator实现）
  ├─ parallel: asyncio.gather 并行执行（orchestrator实现）
  └─ hybrid: 拓扑排序分层并行（orchestrator实现）
  ↓
QualityAgent（质量检查，智能下载专用，两阶段评估）
  ↓ Phase A: 规则评估（0次LLM）→ Phase B: 整体评估（1次LLM）
  ↓ 未通过 → 选择性重试（最多3次）→ 只重试失败任务
  ↓
SummaryAgent（结果总结，1次LLM调用）
  ↓ 生成最终答案 + 执行摘要
  ↓
返回结果（含成本报告、执行路径、质量分数）
```

## 二、决策树设计

**代码位置**: `app/modules/agent_orchestration/decision_tree.py` + `smart_decision_tree.py`

### 基础版 DecisionTree（纯规则）
- 意图识别：关键词匹配（`什么/为什么` → question，`生成/创建` → code_generation）
- 复杂度评估：输入长度 + 是否包含多个子任务分隔符
- 知识库覆盖率：向量检索最高分

### 智能版 SmartDecisionTree（LLM驱动，优先使用）
- 发送带 5 个 few-shot 示例的 prompt 让 LLM 输出 JSON（path/confidence/reasoning）
- LLM 失败时降级到规则分析（字符数 + 知识库覆盖率）
- 集成 CostController，预算不足时强制降级到 simple 路径

```python
# orchestrator.py 初始化逻辑
try:
    self.decision_tree = SmartDecisionTree(llm_provider=..., ...)
except Exception:
    self.decision_tree = DecisionTree(...)  # fallback
```

### 三种执行路径的定义

| 路径 | 占比 | max_steps | 重试 | 质检 | 成本预算 |
|------|------|-----------|------|------|----------|
| simple | 80% | 2 | 否 | 否 | $0.10 |
| standard | 15% | 5 | 是 | 是 | $0.50 |
| complex | 5% | 15 | 是 | 是 | $2.00 |

### 路径参数的实际使用情况（架构缺口）

**重要**：上述参数（max_steps、enable_retry、enable_quality_check、cost_budget、context_window）在 `ExecutionPath` 数据类中定义，但 **orchestrator 从未读取这些字段**。实际控制行为的是：

| 控制维度 | 实际来源 | 路径参数是否生效 |
|---------|---------|----------------|
| 重试次数 | `orchestrator.max_retries`（构造参数，默认2） | 否，`enable_retry` 未被读取 |
| 质检开关 | `plan["requires_quality_check"]`（PlanningAgent 设置） | 否，`enable_quality_check` 未被读取 |
| 最大步数 | PlanningAgent 的子任务分解数量 | 否，`max_steps` 未被读取 |
| 成本预算 | `CostController` 全局预算 | 否，`cost_budget` 未被读取 |
| 上下文窗口 | 未实现 | 否，`context_window` 未被读取 |

路径选择的结果仅用于日志记录和数据库存储（`execution_path` 字段），不影响执行流程。这是一个待完善的架构缺口——决策树的分类结果应该驱动下游行为差异。

## 三、PlanningAgent（任务规划）

**代码位置**: `app/modules/agent_orchestration/agents/planning_agent.py`

**流程**:
1. **意图识别**: 先关键词匹配，匹配不到再调 LLM（1次调用）
2. **知识检索**: 如果有知识库，向量检索 top_k=5 相关片段
3. **复杂度评估**: 基于规则（输入长度 + 关键词）
4. **子任务分解**: 简单任务直接返回1个子任务，复杂任务调 LLM 分解为2-5个子任务（1次调用）
5. **执行策略**: sequential（无依赖）/ parallel（无依赖多任务）/ hybrid（有依赖）

**子任务结构**:
```python
{
    "id": "task_1",
    "type": "knowledge_search | code_analysis | data_processing | design",
    "description": "子任务描述",
    "dependencies": ["task_0"]  # 依赖的前置任务ID
}
```

## 四、ExecutionAgent（策略模式 + 工厂模式）

**代码位置**: `app/modules/agent_orchestration/agents/execution_agent.py`

### 两层策略模式

**第一层：Agent 选择策略（经典策略模式）**
- `ExecutionAgent` 抽象基类定义统一接口 `execute(task, context) -> AgentMessage`
- 6 个具体子类各自实现领域逻辑
- `ExecutionAgentFactory` 工厂按 `agent_type` 字符串创建对应实例
- PlanningAgent 的子任务分解决定每个任务的 `type`，工厂据此选择 Agent

**第二层：执行调度策略（orchestrator 层面）**
- `PlanningAgent._determine_strategy()` 根据复杂度和依赖关系选择策略
- `orchestrator._execute_tasks()` 读取 `plan["strategy"]` 分发到三种执行模式
- 这是调度层面的策略，与 Agent 本身的策略模式是两个独立维度

```
                     调度策略（orchestrator）
                     ├─ sequential: 逐个执行
                     ├─ parallel: asyncio.gather 并行
                     └─ hybrid: 拓扑排序分层并行
                            │
                     每个子任务分发给 ──→ Agent 策略（ExecutionAgent 子类）
                                        ├─ KnowledgeSearchAgent
                                        ├─ CodeAnalysisAgent
                                        ├─ DataProcessingAgent
                                        ├─ DesignAgent
                                        ├─ DownloadExecutionAgent
                                        └─ GitHubExecutionAgent
```

### 具体 Agent 类型

| Agent | 职责 | 依赖 |
|-------|------|------|
| `KnowledgeSearchAgent` | 检索知识库 + LLM 整合知识 | `knowledge_service` |
| `CodeAnalysisAgent` | LLM 生成代码，整合前置任务上下文 | 无 |
| `DataProcessingAgent` | LLM 处理数据 | 无 |
| `DesignAgent` | LLM 生成设计方案 | 无 |
| `DownloadExecutionAgent` | MCP 服务抓取网页/搜索/博客 | `mcp_service` |
| `GitHubExecutionAgent` | GitHub API 搜索仓库/抓取文档 | `github_service` |

### 统一接口

```python
class ExecutionAgent(ABC):
    @abstractmethod
    async def execute(self, task: Dict, context: Optional[Dict]) -> AgentMessage
```

### 工厂创建

```python
class ExecutionAgentFactory:
    @staticmethod
    def create_agent(agent_type: str, llm_provider, ...) -> ExecutionAgent
```

工厂由 `AgentFactory`（`agent_factory.py`）包装，增加实例缓存，避免重复创建。

## 五、执行调度策略详解（orchestrator 实现）

**代码位置**: `app/modules/agent_orchestration/orchestrator.py`

策略由 `PlanningAgent._determine_strategy()` 决定：
- `simple` 复杂度或只有 1 个子任务 → `sequential`
- 无依赖的多任务 → `parallel`
- 有依赖 → `hybrid`

### 顺序执行（sequential）

```python
# orchestrator._execute_sequential()
for task in subtasks:
    agent = agent_factory.create_execution_agent(task["type"])
    result = await agent.execute(task, context)
    previous_results.append(result)  # 前置结果传给下一个任务
```

### 并行执行（parallel）

```python
# orchestrator._execute_parallel()
tasks = [agent.execute(subtask, context) for subtask in subtasks]
results = await asyncio.gather(*tasks, return_exceptions=True)
# 带120秒超时保护
```

### 混合执行（hybrid）— 拓扑排序分层并行

```python
# orchestrator._execute_hybrid()
while len(executed) < len(subtasks):
    # 找出所有依赖已满足的任务
    ready_tasks = [t for t in subtasks if all(dep in executed for dep in t["dependencies"])]
    # 并行执行这一层
    layer_results = await asyncio.gather(*layer_tasks)
    # 记录结果，进入下一层
```

**自动降级**: parallel 模式下检测到任务依赖时自动降级为 hybrid（`orchestrator.py:271-275`）

## 六、QualityAgent（质量检查 — 智能下载专用）

**代码位置**: `app/modules/agent_orchestration/agents/quality_agent.py`

**重要**：QualityAgent 仅用于智能下载场景的质量检查。面试评分使用完全独立的 `UnifiedEvaluationService`（`app/modules/interview/evaluation_service.py`），两者无代码复用关系。

### 两阶段评估架构

**Phase A：逐任务规则评估（0次LLM调用）**
- `_compute_substance()`：基于长度（<200字=0分，200-500字=50分，500+字=80分）、模板内容检测、句子密度评分（0-100）
- `_compute_relevance()`：从用户输入提取关键词，计算内容命中率（宽松模式）
  - 无法提取关键词 → 60分（默认通过）
  - 0命中 → 25分（低于阈值30，标记失败）
  - 有命中 → max(30, 正常计算)，避免误杀
- 单任务通过标准：substance ≥ 40 且 relevance ≥ 30
- 返回 `failed_task_indices` 供选择性重试

**Phase B：整体质量评估（1次LLM调用）**
- 发送元数据摘要 + 800字内容预览（解决截断问题）
- LLM 评估 coverage（覆盖度）和 diversity（多样性）
- 输出 `expanded_keywords`（同义词/相关词），供重试时 Phase A 使用
- Phase B 失败不触发重试，issues 传递给整合阶段

**选择性重试**:
- 只重试 `failed_task_indices` 对应的任务，保留成功结果
- 重试时使用 Phase B 输出的 `expanded_keywords` 提升匹配率
- <50% 任务通过 Phase A → 直接判定失败，不调 LLM

**总分计算**: Phase A 平均分 × 0.6 + Phase B 分数 × 0.4

### 面试评分（独立系统）

面试评估使用 `UnifiedEvaluationService`，与 QualityAgent 无关联：
- 按题型路由：知识题 → `evaluate_knowledge_question()`，项目题 → `evaluate_project_question()`
- 知识题：对比参考答案和关键点评分
- 项目题：四维度评分（真实性、技术深度、深度、表达）
- 异步执行：通过 Redis Streams 消费者组

## 九、面试常见追问

**Q: 这个和 LangChain Agent 有什么区别？**
A: LangChain Agent 是通用的 ReAct 模式（思考-行动-观察循环），我的编排系统是针对特定场景（智能下载+内容生成）设计的五阶段流水线（决策→规划→执行→质检→总结），每个阶段职责明确，支持选择性重试和成本控制，比通用 Agent 更可控。

**Q: 为什么不直接用一个大 prompt 让 LLM 完成所有事？**
A: 拆分多 Agent 的好处：1）每个 Agent 的 prompt 更短更聚焦，输出质量更高；2）可以对每个阶段独立监控和优化；3）质检环节可以发现并纠正前序阶段的错误；4）成本控制可以精确到每个阶段。

**Q: 策略模式体现在哪里？**
A: 有两层策略模式。第一层是 Agent 选择策略：`ExecutionAgent` 抽象基类 + 6 个具体子类（KnowledgeSearchAgent、CodeAnalysisAgent 等），由工厂按 task type 创建，每个子类实现不同的 `execute()` 逻辑。第二层是执行调度策略：orchestrator 根据 `plan["strategy"]` 选择 sequential/parallel/hybrid 三种调度方式，这层在 orchestrator 里实现，不在 Agent 里。两层独立：调度策略决定"什么时候跑"，Agent 策略决定"跑什么"。

**Q: 三种执行路径（simple/standard/complex）有什么区别？**
A: 定义上有区别：simple（max_steps=2, 无重试无质检, $0.10预算）、standard（max_steps=5, 有重试有质检, $0.50）、complex（max_steps=15, 有重试有质检, $2.00）。但实际上 orchestrator 目前没有读取这些参数——质检开关由 PlanningAgent 的 `requires_quality_check` 控制，重试由 orchestrator 的 `max_retries` 控制。路径选择的结果仅用于日志和分析，不影响执行行为。这是一个待完善的架构缺口。

**Q: 任务依赖是怎么处理的？**
A: 子任务通过 `dependencies` 字段声明依赖的前置任务 ID。执行时用拓扑排序分层：没有依赖的任务第一层并行执行，依赖第一层结果的任务第二层执行，以此类推。检测到循环依赖时 break。parallel 模式下如果检测到依赖，自动降级为 hybrid。

**Q: 为什么用编排器显式调度而不是责任链？**
A: 在这个场景下，五个阶段的执行顺序是固定的（决策→规划→执行→质检→总结），不需要每个 handler 自己判断"能不能处理"。编排器显式调度更直观，每个 Agent 职责单一，符合 Python "Explicit is better than implicit" 的哲学。责任链更适合处理链路不固定、需要动态组合的场景。

**Q: QualityAgent 的两阶段评估是怎么设计的？**
A: 解决原来"全有或全无"的问题。Phase A 用纯 Python 规则逐任务检查（0次LLM调用）：内容实质性（长度、模板检测）和主题相关性（关键词匹配）。Phase B 用 LLM 做整体评估（1次调用）：发送元数据摘要+800字预览，评估覆盖度和多样性。两阶段分工：Phase A 管"单个任务是否合格"，Phase B 管"整体搭配是否合理"。

**Q: 选择性重试是怎么实现的？**
A: Phase A 返回 `failed_task_indices`（如 [3, 5]），重试时只重新执行失败任务，保留成功结果。用 `successful_results` 字典跨重试轮次持久化，合并新旧结果后重新质检。原来10个任务失败1个要全部重试，现在只重试那1个。

**Q: expanded_keywords 是什么？**
A: Phase B 的 LLM 评估时，同时输出用户需求的同义词和相关词。比如用户搜"Claude Code 使用方式"，expanded_keywords 可能包含 ["Anthropic", "CLI", "命令行工具"]。重试时这些词合并到 Phase A 的关键词列表，提升匹配率——原来 0 命中的内容可能因为 expanded_keywords 命中而通过。

**Q: QualityAgent 和面试评分是同一个东西吗？**
A: 不是。QualityAgent 只用于智能下载场景（检查下载内容的质量），使用两阶段评估（规则+LLM）。面试评分使用完全独立的 `UnifiedEvaluationService`，按题型路由（知识题对比参考答案、项目题四维度评分），通过 Redis Streams 异步执行。两者无代码复用。
