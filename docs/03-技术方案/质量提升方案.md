# AI 面试质量提升方案

> 文档日期：2026-06-05
> 适用范围：知识库 RAG、动态面试、静态模拟面试、训练计划、质量基准与 CI
> 目标：把系统从“功能可用”提升到“结果可信、训练有效、质量可持续验证”

---

## 一、背景

当前项目已经具备完整的面试训练闭环：

```text
上传简历 / 选择岗位
  ↓
简历分析与诊断
  ↓
项目打磨 / 动态面试 / 标准模拟面试
  ↓
评分报告与教练反馈
  ↓
训练计划与同题复训
```

工程层面也已经有基本质量设施：

- `scripts/quality_check.sh` 串联 Python 编译、Ruff、pytest 和前端构建。
- `tests/quality_baseline_eval.py` 覆盖动态面试的出题、追问、评分和 LLM judge。
- `scripts/rag_eval_*.py` 和 `tests/rag_eval_report.md` 覆盖 RAG 检索评估。
- `tests/quality_baselines/2026-05-29/report.md` 展示动态面试质量基准。

但这些质量信号主要证明“系统能生成、能评分、能跑通”，还不能充分证明：

- 检索结果是否真的相关。
- 回答是否忠实于引用片段。
- 面试题是否能区分候选人真实水平。
- 评分是否能抵抗关键词堆砌。
- 教练反馈是否能让用户下一次回答明显变好。
- 质量报告是否准确反映当前风险。

本方案优先补齐这些质量缺口。

## 三、质量问题地图

## 3.1 检索质量

### 问题 1：Embedding 失败后静默降级为哈希向量

相关文件：

- `app/modules/knowledge_base/vector_service.py`

当前行为：

- `embed_text()` 在外部 embedding 调用失败时把 `_use_real_embedding` 置为 `False`。
- 后续查询和索引会使用 SHA-256 生成 1536 维哈希向量。

影响：

- 哈希向量不是语义向量，相关性没有语义意义。
- 用户看到的是“有检索结果”，但结果可能已经退化为随机相似。
- 一次外部服务失败可能让当前进程后续全部使用降级模式。

改进方向：

- 生产环境禁止哈希向量参与真实问答。
- embedding 服务不可用时返回明确错误或 degraded 状态。
- 允许测试环境显式启用哈希向量，但必须在响应 metadata 中标记。
- 索引时记录 `embedding_provider`、`embedding_model`、`embedding_status`。

验收标准：

- 真实问答路径中，embedding 失败不会返回伪相关答案。
- 测试环境可以显式启用 hash fallback。
- API 响应或日志能区分 real embedding 与 fallback embedding。

### 问题 2：RAG 答案没有忠实性校验

相关文件：

- `app/modules/knowledge_base/rag_service.py`
- `app/modules/knowledge_base/cross_kb_rag_service.py`

当前行为：

- 只有 `references` 为空时拒答。
- 有引用时直接让 LLM 回答。
- 没有检查答案中的每个关键结论是否能被引用片段支撑。

影响：

- 检索片段弱相关时，模型仍可能给出看似完整的答案。
- 推荐追问和正文混在同一段回答中，难以单独评估。
- 用户可能把模型补全内容误认为知识库事实。

改进方向：

- 增加低相关度拒答阈值。
- 生成后做 groundedness 检查，确认主要结论有引用支撑。
- 把 `answer` 和 `suggested_questions` 拆成结构化字段。
- 对无引用、低引用覆盖、引用不匹配分别给不同提示。

验收标准：

- 低相关片段不再生成完整答案。
- RAG answer 至少 90% 的关键句能映射到引用片段。
- 推荐追问可独立展示和评估。

### 问题 3：向量、图谱、重排分数尺度不一致

相关文件：

- `app/modules/knowledge_base/search_channel.py`
- `app/modules/knowledge_graph/graph_search_channel.py`
- `app/modules/knowledge_base/cross_kb_rag_service.py`
- `app/modules/knowledge_base/rerank_service.py`

当前行为：

- 向量检索使用 cosine similarity。
- 图谱检索使用实体命中数量构造启发式分数。
- Cross-Encoder 重排会覆盖 vector chunk 的 `score`。
- 跨 KB 可配置检索中只重排向量结果，图谱结果保留自身分数后混排。

影响：

- 分数排序不可比，图谱结果可能因为分数尺度被错误前置或后置。
- 重排序指标显示没有提升，但报告结论仍称稳定提升。
- 跨 KB 第一条命中质量不足。

改进方向：

- 引入统一 `RetrievalScore`，区分 `raw_score`、`normalized_score`、`channel`、`rerank_score`。
- 合并前按通道做归一化或学习型融合。
- 对图谱结果也进入统一 rerank 或独立校准。
- 评估报告必须按真实指标生成结论。

验收标准：

- 每条引用能显示来自 vector、graph 还是 hybrid。
- 混合检索相比纯向量在 Recall 和 MRR 上有真实提升，否则报告写明无提升。
- 跨 KB Hit@1 从 0.311 提升到 0.45 以上。

## 3.2 问题质量

### 问题 4：题目生成缺少后验质量验证

相关文件：

- `app/modules/interview/question_service.py`
- `app/prompts/interview-question-skill-system.md`
- `app/prompts/interview-question-resume-system.md`

当前行为：

- 简历题和方向题并行生成。
- 有简历时固定按 60% 简历题、40% 方向题分配。
- LLM 少出题时只记录 warning，不做补齐。
- fallback 题没有参考答案和关键得分点。

影响：

- 实际题目数量可能低于用户要求。
- fallback 题进入无参考评分路径，知识题最高分被保守限制到 75。
- 固定配比不适合所有岗位和简历质量。

改进方向：

- 增加 `QuestionQualityValidator`：
  - 数量是否精确。
  - 是否重复。
  - 是否与 JD 对齐。
  - 是否有区分度。
  - 知识题是否带 `referenceAnswer` 和 `keyPoints`。
  - 项目题是否有简历证据。
- 少题时自动补齐，重复时自动重写。
- 简历材料弱时降低项目题比例，JD 明确时提高岗位题比例。

验收标准：

- `question_count` 命中率达到 100%。
- 题目重复率低于 5%。
- fallback 知识题也有可评分基线。
- 每套题输出 `quality_report` 供调试和评估。

### 问题 5：历史去重依赖短文本摘要

相关文件：

- `app/modules/interview/question_service.py`
- `app/modules/interview/persistence_service.py`

当前行为：

- 历史去重主要依赖 `topicSummary` 或问题前 30 字。

影响：

- 同一知识点换个问法可能重复出现。
- 不同知识点如果摘要相近，可能被误判为重复。
- 用户多轮训练后会感觉题目变化不大。

改进方向：

- 为题目生成 `topic_key` 和 `semantic_fingerprint`。
- 使用 embedding 或规则归一化做语义去重。
- 记录重复原因：同 topic、同项目、同能力维度、同题干。

验收标准：

- 同一用户最近 30 天内，同 topic 重复率可观测。
- 低分 topic 可以有意复训，普通 topic 默认避重。

## 3.3 评分质量

### 问题 6：动态评分容易被关键词投机

相关文件：

- `app/modules/interview/dynamic_service.py`

当前行为：

- 动态评分主要依赖长度、结构词、topic 命中、具体技术词、泛化词和跑题词。
- 命中多个具体技术词可以显著加分。

影响：

- 用户堆关键词可能获得较高分。
- 回答事实错误但包含技术词时，评分未必能识别。
- 低分反馈可控，但高分可信度不足。

改进方向：

- 把规则评分定位为 fast signal，不直接等同最终能力分。
- 增加 adversarial answer 测试集：
  - 关键词很多但事实错误。
  - 结构完整但答非所问。
  - 很短但准确。
  - 长篇泛泛而谈。
- 对高分回答做 LLM judge 抽检。
- 对知识题引入 topic-specific 必答点。

验收标准：

- 关键词堆砌错误答案不能超过 60 分。
- 强答案、普通答案、泛泛答案、跑题答案排序稳定。
- 与 LLM judge 的分差中位数低于 10 分。

### 问题 7：静态评分过度依赖单次 LLM 输出

相关文件：

- `app/modules/interview/evaluation_service.py`
- `app/prompts/eval-knowledge-system.md`
- `app/prompts/eval-project-system.md`

当前行为：

- 知识题有参考答案和 key points 时走逐点评估。
- 缺少参考答案时走保守评分，最高 75。
- 项目题由 LLM 直接输出四维评分。

影响：

- 同一道题不同模型或同模型不同调用可能出现评分波动。
- 项目题真实性判断缺少可验证证据要求。
- 缺少“评分可信度”和“需要人工复核”的明确输出。

改进方向：

- 每题评估输出 `confidence`、`evidence_count`、`needs_review`。
- 项目题强制提取证据项：数据量、个人动作、技术取舍、结果指标、失败边界。
- 引入二次校准：规则可信度 + LLM 分数 + 历史均值。

验收标准：

- 每道题都能解释为什么是这个分数。
- 低证据高分自动进入复核。
- 项目题维度分和总分权重一致。

## 3.4 指导质量

### 问题 8：教练反馈偏结构，不够定位到内容

相关文件：

- `app/modules/interview/dynamic_service.py`
- `app/modules/interview/evaluation_service.py`

当前行为：

- coach hint 主要提供回答结构和缺口方向。
- 教练模式低于 85 分就同题重答，下一题仍是原主问题。

影响：

- 用户知道要补“结构、指标、边界”，但不知道具体补哪一句。
- 多次重答可能变成重复回答，而不是针对缺口刻意练习。

改进方向：

- 把反馈拆成四层：
  - 面试官判断。
  - 当前答案具体问题。
  - 下一版只补一个目标。
  - 重答约束。
- `next_question` 不再总是原题，可以生成针对性重答指令。
- 引入重答前后 diff：补了哪些点、仍缺哪些点。

验收标准：

- 每次 coach retry 都有明确单点目标。
- 用户重答后，系统能展示增量变化。
- 训练任务能回溯到具体题、具体缺口、具体改法。

### 问题 9：训练计划和进度绑定不稳定

相关文件：

- `app/modules/training/service.py`

当前行为：

- 更新任务进度时重新生成当前任务 lookup。
- 如果计划规则变化，旧任务可能被判定为过期。

影响：

- 用户完成过的训练任务可能刷新后无法更新。
- 训练闭环不够稳定，难以做长期趋势。

改进方向：

- 持久化训练计划快照。
- 任务 ID 由稳定源生成：session、question、topic、weakness。
- 已生成任务允许在一段时间内继续更新状态。

验收标准：

- 计划刷新不丢进度。
- 低分题复训、简历修改、动态 topic 重练都能进入趋势图。

## 3.5 质量基准质量

### 问题 10：质量基准覆盖不到真实核心风险

相关文件：

- `tests/quality_baseline_eval.py`
- `tests/rag_eval_report.md`
- `scripts/rag_eval_runner.py`

当前行为：

- 动态面试基准主要检查题型配比、topic 命中、分数排序、追问动作。
- `check_rag_quality` 没有接入主流程。
- RAG 报告结论和表格指标存在冲突。

影响：

- “100% 通过”容易被误读为系统质量全面达标。
- 检索、引用、忠实性、指导效果没有形成统一基准。

改进方向：

- 把质量线改成 6 类：
  - 检索质量。
  - 答案忠实性。
  - 出题质量。
  - 追问质量。
  - 评分质量。
  - 指导质量。
- 每条质量线都有可复现数据集和门槛。
- 报告结论必须由指标自动推导。

验收标准：

- 质量报告中每个“可发布”结论都能追溯到指标。
- RAG 和面试质量共用版本化 baseline。
- 新增失败和已修复失败能稳定对比。

## 五、分阶段实施路线

## Phase 0：修复质量信号可信度

周期：1-2 天。

目标：先让质量报告说真话。

任务：

1. 格式化当前 7 个 Ruff format 失败文件。
2. 调整 `scripts/quality_check.sh`，输出每个阶段的结果摘要。
3. 修复 RAG 报告结论文案，禁止写与指标冲突的结论。
4. 把 `check_rag_quality` 接入质量基准，至少覆盖 no-hit 和低置信引用。
5. 在质量报告中明确区分“动态面试质量”和“RAG 质量”。

验收：

- `./scripts/quality_check.sh` 完整通过。
- 质量基准报告不再把未检查项写成 100%。
- RAG 报告结论和表格指标一致。

## Phase 1：检索防线

周期：3-5 天。

目标：宁可拒答，也不伪造可靠感。

任务：

1. 禁止生产问答使用 hash embedding。
2. 增加 embedding 状态字段。
3. 增加检索低相关阈值。
4. 拆分 `answer` 和 `suggested_questions`。
5. 增加 answer groundedness 检查。
6. 统一 vector、graph、rerank 分数结构。

验收：

- embedding 服务不可用时不会生成伪答案。
- 低相关查询返回明确的“不足以回答”。
- RAG 引用支撑率可量化。

## Phase 2：题目质量防线

周期：3-5 天。

目标：每道题都有出题理由、评分锚点和去重依据。

任务：

1. 新增 `QuestionQualityValidator`。
2. 增加题目补齐和去重重写。
3. 为 fallback 知识题补参考答案和 key points。
4. 动态调整简历题与方向题比例。
5. 持久化 `topic_key` 和 `semantic_fingerprint`。

验收：

- 题目数量稳定命中。
- 同一用户近期题目重复率可观测。
- 无评分锚点的知识题显著减少。

## Phase 3：评分校准防线

周期：5-7 天。

目标：分数不仅能排序，还能解释可信度。

任务：

1. 动态评分增加 adversarial 测试集。
2. 规则评分输出 `confidence` 和命中证据。
3. 高分回答或低证据回答触发 LLM judge 抽检。
4. 项目题抽取证据项后再评分。
5. 报告中展示低可信题和复核原因。

验收：

- 关键词堆砌错误答案不能拿高分。
- 评分报告能说明证据数量和缺口。
- 低可信评分进入训练计划或复核列表。

## Phase 4：教练反馈闭环

周期：5-7 天。

目标：让用户知道下一版具体该补什么。

任务：

1. coach hint 改为单点重答目标。
2. 每轮 retry 生成针对性重答指令。
3. 增加重答前后 diff。
4. 训练计划持久化任务快照。
5. 趋势图展示同题复训增量。

验收：

- 每个重答任务都有明确缺口和目标。
- 用户重答后能看到增量变化。
- 训练任务刷新后不丢进度。

## 六、推荐测试补充

## 6.1 RAG 测试

新增测试方向：

- embedding 失败不会回退生成伪答案。
- hash embedding 只允许测试环境显式启用。
- 低相关 query 返回拒答。
- RAG answer 引用编号必须存在于 references。
- 推荐追问从 answer 中拆出。
- vector 和 graph score 不可直接混排。

建议文件：

- `tests/test_rag_guardrails.py`
- `tests/test_rag_groundedness.py`
- `tests/test_retrieval_score_fusion.py`

## 6.2 出题测试

新增测试方向：

- LLM 少出题时自动补齐。
- 重复题被改写。
- fallback 知识题包含 reference answer 和 key points。
- 简历弱证据时减少项目题。
- JD 明确时岗位题占比提高。

建议文件：

- `tests/test_question_quality_validator.py`
- `tests/test_question_generation_repair.py`

## 6.3 评分测试

新增测试方向：

- 关键词堆砌但事实错误不能高分。
- 很短但准确的回答不能过低。
- 项目题没有个人贡献不能高真实性分。
- 结构完整但答非所问必须降分。
- LLM judge 分歧样本进入 review。

建议文件：

- `tests/test_dynamic_scoring_adversarial.py`
- `tests/test_evaluation_confidence.py`

## 6.4 指导测试

新增测试方向：

- coach retry 必须有单点目标。
- 同题重答后能计算 delta。
- 训练任务刷新后仍可更新进度。
- 训练任务能追溯到原 session 和 question。

建议文件：

- `tests/test_coach_retry_targeting.py`
- `tests/test_training_plan_persistence.py`

## 七、发布门槛

建议把发布状态拆成三档。

## 可演示

- 工程质量脚本完整通过。
- 动态面试基准通过率 >= 85%。
- RAG no-hit 诚实率 >= 95%。
- 已知报告结论与指标一致。

## 可内测

- 动态面试基准通过率 >= 90%。
- RAG answer 引用支撑率 >= 85%。
- 跨 KB Hit@1 >= 0.40。
- 关键词投机样本拦截率 >= 80%。
- 教练反馈单点目标覆盖率 >= 90%。

## 可公开试用

- 动态面试基准通过率 >= 95%。
- RAG answer 引用支撑率 >= 90%。
- 跨 KB Hit@1 >= 0.45。
- 评分与 LLM judge 分差中位数 <= 10 分。
- 用户训练任务刷新不丢进度。

## 八、建议优先级

第一优先级：

1. 禁止生产 RAG 使用 hash embedding。
2. 修复质量报告结论与指标不一致。
3. 接入 RAG 质量检查。
4. 增加检索低相关拒答。

第二优先级：

1. 增加题目质量 validator。
2. 为 fallback 题补评分锚点。
3. 动态评分加入 adversarial 测试。
4. 教练反馈改成单点重答目标。

第三优先级：

1. 统一检索分数融合。
2. 持久化训练计划快照。
3. 建立人工标注小样本。
4. 把质量报告做成版本化 dashboard。
