## 二、AI 面试 Agent 流程架构

### 2.1 流程类型：**固定流程编排**

当前面试 Agent 采用**固定流程编排**方式，不是自主决策的 Agent。

**流程特征：**
- 线性执行：创建会话 → 生成题目 → 逐题问答 → 提交评估 → 生成报告
- 无循环反馈：不会根据用户回答动态调整后续题目
- 无自主决策：所有题目在面试开始前一次性生成完毕

### 2.2 核心流程

```
┌─────────────────┐
│  创建面试会话    │
│ (session_service)│
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  并行生成题目    │  ← 简历题 + 方向题并行调用 LLM
│(question_service)│
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  逐题问答交互    │  ← 前端逐题提交，后端记录答案
│ (session_service)│
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  入队评估任务    │  ← 发送到 Redis Stream
│  (async_tasks)   │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  后台评估执行    │  ← Worker 消费任务
│(evaluation_service)│
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  生成面试报告    │
│ (session_service)│
└─────────────────┘
```

### 2.3 是否有循环

**当前实现：无循环**

- 题目生成阶段：一次性生成所有题目（包括主问题 + 追问），不会根据回答动态生成
- 问答阶段：线性遍历题目列表，无条件跳转或循环
- 评估阶段：批量评估所有问答记录，无迭代优化

**追问机制说明：**
- 追问题目在面试开始前已预生成（`followUps` 字段）
- 追问数量固定（配置项 `follow_up_count`，默认 1 条，最多 2 条）
- 追问内容不依赖用户实际回答，属于"预设追问"而非"动态追问"

## 三、出题服务技术方案

### 3.1 出题策略

**文件位置：** `app/modules/interview/question_service.py`

**核心逻辑：**

1. **有简历模式**：简历题（60%）+ 方向题（40%）并行生成
   - 简历题：基于简历内容出项目经验题
   - 方向题：基于 Skill 定义出技术方向题
   - 并行调用：使用 `asyncio.gather()` 同时请求 LLM

2. **无简历模式**：纯方向题
   - 根据 Skill 的 categories 分配题目数量
   - 按权重比例分配（`calculate_allocation`）

3. **历史去重**：
   - 查询该简历在同一 Skill 下的历史题目
   - 将历史题目的 `topic_summary` 传入 Prompt
   - 要求 LLM 避免重复考察相同知识点

### 3.2 Prompt 工程

**Prompt 文件：**
- `app/prompts/interview-question-skill-system.md`：方向题系统提示词
- `app/prompts/interview-question-skill-user.md`：方向题用户提示词
- `app/prompts/interview-question-resume-system.md`：简历题系统提示词
- `app/prompts/interview-question-resume-user.md`：简历题用户提示词

**结构化输出：**
- 使用 LangChain 的 `PydanticOutputParser`
- 输出模型：`_QuestionListDTO`（包含 `questions` 列表）
- 每个问题包含：`question`、`type`、`category`、`topicSummary`、`followUps`

### 3.3 降级策略

**降级链路：**
1. LLM 调用失败 → 回退到预设问题（`GENERIC_FALLBACK_QUESTIONS`）
2. 简历题失败 → 全部改为方向题
3. 方向题失败 → 使用 Skill categories 生成模板问题

## 四、评估服务技术方案

### 4.1 评估架构：**分批评估 + 二次汇总**

**文件位置：** `app/modules/interview/evaluation_service.py`

**核心流程：**

```
┌──────────────────┐
│  所有问答记录     │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  分批评估         │  ← 每批最多 8 题
│ (_evaluate_batch) │  ← 并行调用 LLM
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  聚合批次结果     │  ← 合并所有批次的评分和反馈
│ (_merge_*)        │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  二次汇总         │  ← 再次调用 LLM 生成总评
│(_summarize_batch) │  ← 输入：分类汇总 + 题目亮点
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  构建最终报告     │
│ (_build_report)   │
└──────────────────┘
```

### 4.2 分批策略

**批次大小：** 8 题/批（`_batch_size = 8`）

**原因：**
- 避免单次 Prompt 过长导致 LLM 输出质量下降
- 减少单次调用失败的影响范围
- 提高并发处理能力（未来可改为真正并行）

### 4.3 降级保障

**降级链路：**
1. 批次评估失败 → 该批次返回 `None`，不影响其他批次
2. 二次汇总失败 → 使用批次聚合结果（`fallback_feedback`、`fallback_strengths`、`fallback_improvements`）
3. 结构化解析失败 → 重试最多 3 次（`structured_max_attempts`）

### 4.4 Prompt 工程

**Prompt 文件：**
- `app/prompts/interview-evaluation-system.md`：批次评估系统提示词
- `app/prompts/interview-evaluation-user.md`：批次评估用户提示词
- `app/prompts/interview-evaluation-summary-system.md`：汇总评估系统提示词
- `app/prompts/interview-evaluation-summary-user.md`：汇总评估用户提示词

**输出模型：**
- 批次评估：`_BatchReportDTO`（包含 `questionEvaluations`、`overallFeedback`、`strengths`、`improvements`）
- 二次汇总：`_SummaryDTO`（包含 `overallFeedback`、`strengths`、`improvements`）

## 五、RAG 知识库技术方案

### 5.1 检索方式：**本地向量相似度检索**

**文件位置：** `app/modules/knowledge_base/rag_service.py`

**当前实现：**
- **向量化方法**：SHA-256 哈希 → 固定 16 维向量（`EMBEDDING_DIMENSIONS = 16`）
- **相似度计算**：余弦相似度（Cosine Similarity）
- **检索流程**：遍历所有 chunks，计算相似度，排序取 Top-K
- **存储方式**：embedding 以 JSON 字符串存储在 PostgreSQL 的 `embedding_json` 字段

**技术特点：**
- ✅ 无需外部向量数据库（pgvector、Milvus、Qdrant 等）
- ✅ 本地联调方便，无额外依赖
- ❌ 向量质量低（哈希向量无语义信息）
- ❌ 检索性能差（全表扫描，O(n) 复杂度）
- ❌ 无法支持大规模知识库（>1000 文档）

### 5.2 文本切分策略

**文件位置：** `app/modules/knowledge_base/vector_service.py`

**切分算法：段落优先 + 滑动窗口**

**核心参数：**
- `chunk_size`：900 字符（默认）
- `overlap`：120 字符（默认）

**切分逻辑：**

```python
def split_text(text, chunk_size=900, overlap=120):
    # 1. 文本归一化：统一换行符、去除多余空行
    normalized = _normalize_text(text)
    
    # 2. 按双换行符分割段落
    paragraphs = normalized.split("\n\n")
    
    # 3. 段落优先合并
    for paragraph in paragraphs:
        if len(current + paragraph) <= chunk_size:
            current += paragraph  # 合并到当前 chunk
        else:
            # 保存当前 chunk，带 overlap 开始新 chunk
            chunks.append(current)
            current = current[-overlap:] + paragraph
    
    # 4. 超长段落强制切分
    if len(paragraph) > chunk_size:
        slices = _split_long_paragraph(paragraph, chunk_size, overlap)
```

**特点：**
- ✅ 保持段落完整性（优先不切断段落）
- ✅ 滑动窗口保证上下文连续性
- ✅ 超长段落自动强制切分
- ❌ 未考虑语义边界（句子、标题、列表等）
- ❌ 固定窗口大小，未根据文档类型自适应

### 5.3 重排序（Reranking）

**当前实现：无重排序**

**检索流程：**
1. 查询改写（Query Rewriting）：调用 LLM 改写用户问题为检索查询
2. 向量检索：计算余弦相似度，排序取 Top-K
3. 直接返回：Top-K 结果直接传给 LLM 生成答案

**缺失能力：**
- ❌ 无二次精排（Cross-Encoder Reranking）
- ❌ 无多路召回融合（BM25 + 向量混合检索）
- ❌ 无 MMR（Maximal Marginal Relevance）去重

### 5.4 RAG 问答流程

**文件位置：** `app/modules/knowledge_base/rag_service.py`

**核心流程：**

```
用户问题
   │
   ▼
┌─────────────────┐
│  查询改写        │  ← 调用 LLM 改写为检索查询
│ (_rewrite_query) │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  向量检索        │  ← 遍历所有 chunks，计算相似度
│ (_search_chunks) │  ← 排序取 Top-K（默认 4）
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  生成答案        │  ← 将 Top-K 片段拼接为 Prompt
│(_generate_answer)│  ← 调用 LLM 生成答案
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  保存问答记录    │
└─────────────────┘
```

**Prompt 模板：**

```
用户问题：{question}
检索查询：{rewritten_query}

参考片段：
[片段1] 标题: {title}
相关度: {score}
内容: {content_preview}

[片段2] ...

请基于这些片段回答，并在结尾简短说明依据来自哪些片段。
```

### 5.5 流式输出

**实现方式：SSE（Server-Sent Events）**

**事件类型：**
- `meta`：返回 session_id 和改写后的查询
- `chunk`：分块返回答案内容（每块 120 字符）
- `references`：返回参考片段列表
- `done`：返回完整答案

**注意：** 当前流式输出是"伪流式"，实际是先完整生成答案，再分块推送。真正的流式应该是 LLM 生成过程中逐 token 推送。

### 6.1 消息队列：Redis Stream

**使用场景：**
1. 简历分析（已改为同步，Stream 代码已移除）

```
┌──────────────┐

└──────┬───────┘
       │
       ▼
┌──────────────┐
│ Redis Stream │  ← 持久化任务队列
└──────┬───────┘
       │
       ▼

```


## 七、LLM 调用封装

### 7.1 Provider 注册表

**文件位置：** `app/common/ai/llm_provider.py`

**当前实现：**
- 单一 Provider：DashScope（阿里云百炼）
- 模型：qwen-plus
- 参数：temperature=0.7, max_tokens=4096, timeout=180s

**扩展方式：**
```python
llm_registry.register("openai", ChatOpenAI(...))
llm_registry.register("claude", ChatAnthropic(...))
```

### 7.2 结构化输出

**文件位置：** `app/common/ai/structured_output.py`

**核心机制：**
- 使用 LangChain 的 `PydanticOutputParser`
- 自动生成 JSON Schema 格式说明
- 失败重试：最多 3 次（`structured_max_attempts`）
- 重试策略：附加严格 JSON 指令 + 上次错误信息

**调用方式：**
```python
result = await structured_output_invoker.invoke(
    chat_model=chat_model,
    system_prompt="你是面试官",
    user_prompt="请出 5 道题",
    output_model=QuestionListDTO,
    error_code=ErrorCode.INTERVIEW_QUESTION_GENERATION_FAILED,
)
```

### 7.3 调用模式

**当前模式：非流式调用（`ainvoke`）**

**原因：**
- Windows 环境下 `astream()` 存在兼容性问题（已在 PROGRESS.md 记录）
- 结构化输出需要完整 JSON，无法流式解析
- 评估和出题场景不需要流式输出

**流式场景：**
- 知识库 RAG 问答（SSE 流式输出）
- 但实际仍是先 `ainvoke` 生成完整答案，再分块推送

## 八、优化方向建议

### 8.1 RAG 知识库优化

**高优先级：**
1. **向量化升级**
   - 替换为真实 Embedding 模型（如 text-embedding-3-small、bge-large-zh）
   - 向量维度：768 或 1024
   - 预期提升：检索准确率 +30%

2. **向量数据库**
   - 引入 pgvector 扩展（PostgreSQL 原生支持）
   - 或使用专用向量数据库（Qdrant、Milvus）
   - 预期提升：检索性能 100x（O(n) → O(log n)）

3. **重排序（Reranking）**
   - 引入 Cross-Encoder 模型（如 bge-reranker-large）
   - 在 Top-K 结果上二次精排
   - 预期提升：Top-3 准确率 +15%

**中优先级：**
4. **混合检索**
   - BM25（关键词检索）+ 向量检索
   - 加权融合（如 0.3 * BM25 + 0.7 * Vector）
   - 预期提升：长尾查询召回率 +20%

5. **文本切分优化**
   - 语义切分：基于句子边界、标题层级
   - 自适应窗口：根据文档类型调整 chunk_size
   - 预期提升：片段完整性 +25%

6. **查询改写增强**
   - 多查询生成（Multi-Query）
   - 假设性文档嵌入（HyDE）
   - 预期提升：复杂查询召回率 +18%

### 8.2 AI 面试 Agent 优化

**高优先级：**
1. **动态追问**
   - 根据用户回答质量决定是否追问
   - 追问内容基于回答生成，而非预设
   - 预期提升：面试深度 +40%

2. **自适应难度**
   - 根据前几题表现动态调整后续难度
   - 引入 IRT（Item Response Theory）模型
   - 预期提升：面试区分度 +30%

**中优先级：**
3. **Agent 化改造**
   - 引入 ReAct 或 Function Calling 模式
   - Agent 自主决定：继续追问 / 切换话题 / 结束面试
   - 预期提升：面试灵活性 +50%

4. **实时评估**
   - 每题回答后立即评分（而非全部答完再评估）
   - 根据实时评分调整后续策略
   - 预期提升：用户体验 +35%

### 8.3 评估服务优化

**高优先级：**
1. **真正并行评估**
   - 当前分批是串行的，改为真正并行调用
   - 使用 `asyncio.gather()` 并行评估所有批次
   - 预期提升：评估速度 3-5x

2. **评估缓存**
   - 相同问题+答案的评估结果缓存
   - 使用 Redis 缓存评分和反馈
   - 预期提升：重复评估速度 10x

**中优先级：**
3. **多模型评估**
   - 使用多个 LLM 评估同一答案
   - 投票或加权平均得到最终分数
   - 预期提升：评估稳定性 +25%

4. **参考答案库**
   - 预先生成标准答案和评分标准
   - 评估时对比标准答案
   - 预期提升：评估一致性 +30%

### 8.4 系统架构优化

**高优先级：**
1. **LLM 调用池化**
   - 引入连接池和限流
   - 避免并发过高导致 API 限流
   - 预期提升：稳定性 +40%

2. **Prompt 版本管理**
   - Prompt 文件加版本号
   - 支持 A/B 测试不同 Prompt
   - 预期提升：迭代效率 +50%

**中优先级：**
3. **可观测性**
   - LLM 调用链路追踪（OpenTelemetry）
   - Token 消耗统计和成本分析
   - 预期提升：问题定位效率 +60%

4. **降级策略完善**
   - 更细粒度的降级开关
   - 降级后的用户提示优化
   - 预期提升：可用性 +20%

## 九、技术债务清单

### 9.1 已知问题

1. **RAG 向量化质量低**
   - 当前使用 SHA-256 哈希，无语义信息
   - 影响：检索准确率低，用户体验差
   - 优先级：P0

2. **RAG 检索性能差**
   - 全表扫描，O(n) 复杂度
   - 影响：知识库规模受限（<1000 文档）
   - 优先级：P0

3. **面试流程固定**
   - 无法根据回答动态调整
   - 影响：面试深度和灵活性不足
   - 优先级：P1

4. **评估串行执行**
   - 分批评估是串行的，速度慢
   - 影响：评估耗时长（>30s）
   - 优先级：P1

5. **LLM 流式输出未启用**
   - 当前使用 `ainvoke`，无法流式返回
   - 影响：用户等待时间长
   - 优先级：P2

### 9.2 技术选型风险

1. **单一 LLM Provider**
   - 当前仅支持 DashScope
   - 风险：API 故障或限流时无降级
   - 建议：接入多个 Provider（OpenAI、Claude、本地模型）

2. **Redis Stream 单点**
   - 当前 Redis 无高可用配置
   - 风险：Redis 故障导致任务丢失
   - 建议：引入 Redis Sentinel 或 Cluster

3. **PostgreSQL 存储向量**
   - 当前 embedding 存储为 JSON 字符串
   - 风险：查询性能差，无法使用向量索引
   - 建议：迁移到 pgvector 或专用向量数据库

## 十一、总结

### 11.1 当前技术特点

**优势：**
- ✅ 架构清晰，模块解耦良好
- ✅ 异步任务机制完善（Redis Stream）
- ✅ 降级策略完备，容错性强
- ✅ Prompt 工程规范，易于迭代

**劣势：**
- ❌ RAG 检索质量和性能差（哈希向量 + 全表扫描）
- ❌ 面试流程固定，缺乏动态调整能力
- ❌ 评估速度慢（串行批次评估）
- ❌ 单一 LLM Provider，无多模型支持

### 11.2 优化优先级

**P0（立即优化）：**
1. RAG 向量化升级（真实 Embedding 模型）
2. 引入 pgvector 或向量数据库

**P1（近期优化）：**
3. 评估并行化
4. 动态追问机制
5. LLM 调用池化

**P2（中期优化）：**
6. 混合检索（BM25 + Vector）
7. Agent 化改造
8. 多模型评估

### 11.3 预期收益

完成 P0 + P1 优化后：
- RAG 检索准确率：40% → 75%
- RAG 检索延迟：500ms → 50ms
- 评估速度：30s → 10s
- 面试深度：+40%
- 系统稳定性：+50%
