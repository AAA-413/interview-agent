# 性能优化优先级

> 文档日期：2026-06-05  
> 用途：基于当前代码静态审计，整理性能问题的处理优先级、实施方向和验收指标。本文不包含压测结果，后续需要通过 `EXPLAIN ANALYZE`、接口 p95、worker 队列积压和前端渲染耗时验证。

---

## 一、结论

当前项目的性能风险主要集中在三类：

1. **查得慢**：知识库 RAG 使用 pgvector 相似度排序，但缺少 HNSW 向量索引，数据量上来后容易退化成大范围扫描和排序。
2. **等得死**：部分 `async def` 内部调用同步 I/O 或 CPU 任务，上传、解析、Embedding、对象存储等操作会阻塞事件循环。
3. **干活的人太少**：Redis Stream 每类任务默认只有一个 worker 串行消费，知识库索引、简历分析、面试评估容易排队。

建议先处理这三个基础问题，再优化接口返回体、详情分页、RAG 调用链和前端渲染体验。

---

## 二、优先级总览

| 优先级 | 优化项 | 目标 | 典型收益 |
| --- | --- | --- | --- |
| P0 | 增加 pgvector HNSW 索引 | 降低知识库向量检索耗时 | RAG 检索从大范围扫描变成近邻图检索 |
| P0 | 移除 async 热路径中的同步阻塞 | 避免单个上传、解析、Embedding 调用卡住 API 事件循环 | 提升并发上传、问答、流式输出稳定性 |
| P0 | worker 做成可横向扩展 | 后台任务可通过增加 worker 实例提升吞吐 | 降低知识库索引、简历分析、面试评估排队时间 |
| P1 | 列表字段裁剪、详情分页/懒加载 | 减少大文本、大 JSON 的无效传输和渲染 | 列表页更快，详情页不被长文档拖慢 |
| P1 | 优化 RAG 调用链 | 减少单次问答中的 LLM 调用次数 | 降低 p95 延迟和模型成本 |
| P1 | 优化图谱检索和兜底检索 | 避免 `ILIKE '%keyword%'` 和 Python 全量相似度计算 | 大知识库下检索更稳定 |
| P1 | 前端轮询和流式 Markdown 渲染优化 | 降低浏览器主线程压力和接口轮询压力 | 长回答、长报告不卡顿 |
| P2 | 指标监控和性能基线 | 建立可回归验证的性能面板 | 后续优化有量化依据 |

---

## 三、P0：必须优先处理

### 3.1 增加 pgvector HNSW 索引

**涉及代码：**

- `app/modules/knowledge_base/models.py`
- `app/modules/knowledge_base/search_channel.py`
- `app/modules/knowledge_base/cross_kb_rag_service.py`

**当前问题：**

`knowledge_chunks.embedding` 存储了向量数据，查询时会按照 `cosine_distance(query_embedding)` 排序取 top k。当前模型定义中只有普通字段索引，没有针对 `embedding` 的 HNSW/IVFFlat 向量索引。

知识库小的时候影响不明显；chunk 数量变大后，数据库需要比较大量向量并排序，RAG 问答延迟会明显上升。

**建议方案：**

通过数据库迁移增加 HNSW 索引：

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_knowledge_chunks_embedding_hnsw
ON knowledge_chunks
USING hnsw (embedding vector_cosine_ops);
```

如果迁移工具默认包裹事务，需要注意 `CREATE INDEX CONCURRENTLY` 不能放在普通事务内执行。可以改为非并发建索引，或在迁移脚本中使用 autocommit。

**补充建议：**

- 保留 `knowledge_base_id` 普通索引，用于过滤知识库范围。
- 使用 `EXPLAIN ANALYZE` 验证查询计划是否走向量索引。
- 如果单库 chunk 极大，再评估是否需要按知识库分区、分表或引入 Qdrant/Milvus。

**验收标准：**

- 向量检索查询计划出现 HNSW 索引扫描。
- 典型知识库 top k 检索耗时可稳定控制在可接受范围内。
- 新增/重建索引过程不会长时间阻塞线上读写。

---

### 3.2 移除 async 热路径中的同步阻塞

**涉及代码：**

- `app/infrastructure/file/file_storage_service.py`
- `app/infrastructure/file/document_parse_service.py`
- `app/modules/knowledge_base/vector_service.py`
- `app/modules/knowledge_base/async_tasks.py`

**当前问题：**

项目使用 FastAPI 和 SQLAlchemy async，但部分 `async def` 内部仍在执行同步操作：

- S3/MinIO 上传、下载、删除使用同步 `boto3`。
- PDF/DOCX 解析是同步 CPU/I/O 操作。
- Embedding 调用里存在同步 HTTP 客户端或同步 SDK。
- 知识库分块后逐 chunk 串行生成 embedding。

这些操作会占住事件循环或 worker，导致其他请求、流式输出、后台任务被拖慢。

**建议方案：**

按照风险从高到低处理：

1. 对象存储操作改为 `aioboto3`，或临时使用 `asyncio.to_thread(...)` 包装同步 `boto3`。
2. PDF/DOCX 解析移到线程池或后台 worker，不在 API 请求事件循环里直接执行。
3. Embedding HTTP 调用改为 `httpx.AsyncClient`；不支持异步的 SDK 先用 `asyncio.to_thread(...)` 隔离。
4. 知识库索引时支持批量 embedding，至少做有界并发，避免逐 chunk 串行等待外部 API。

**验收标准：**

- 上传大文件、解析文档、构建知识库时，普通接口响应不会明显变慢。
- async 热路径中不再直接调用明显的同步网络 I/O。
- worker 中的耗时任务有明确并发上限，不会无限制占用线程或模型调用额度。

### 3.3 worker 做成可横向扩展

**涉及代码：**

- `app/main.py`
- `app/infrastructure/redis/stream_worker.py`
- `app/common/base_async_task.py`
- `app/modules/resume/async_tasks.py`
- `app/modules/interview/async_tasks.py`
- `app/modules/knowledge_base/async_tasks.py`

**当前问题：**

应用启动时会为简历分析、面试评估、知识库索引分别创建 worker，但每类任务默认只有一个 worker 消费；`read_count=1`，任务基本串行处理。

如果某个知识库索引任务耗时 2 分钟，后续同类型任务只能排队。并发用户上传简历、构建知识库、提交面试评估时，队列会出现积压。

**建议方案：**

1. 将 API 进程和 worker 进程拆分运行，避免后台重任务影响在线请求。
2. 支持通过环境变量配置每类 worker 并发数，例如：
   - `RESUME_WORKER_CONCURRENCY=2`
   - `INTERVIEW_WORKER_CONCURRENCY=2`
   - `KB_INDEX_WORKER_CONCURRENCY=4`
3. Redis Stream 使用同一个 consumer group，不同 worker 实例使用不同 consumer name，让 Redis 分配不同消息。
4. `read_count` 支持配置，并在 worker 内部用有界并发处理任务。
5. 增加 pending 消息恢复、重试次数、死信队列和幂等保护。

**验收标准：**

- 同一类任务可以启动多个 worker 实例并发消费。
- 增加 worker 数量后，队列积压下降速度明显提升。
- 任务失败后可重试；重复投递不会写坏业务数据。
- API 进程重启不会导致后台任务丢失。

## 四、P1：紧随其后的优化

### 4.1 列表字段裁剪和详情分页

**问题：**

简历、知识库、面试列表接口倾向于查询完整实体，包含 `resume_text`、`source_text`、大 JSON、chunks、answers 等列表页不需要的数据。知识库详情也会一次性返回完整原文和 chunks，前端直接 Markdown 渲染。

**建议：**

- 列表接口只 select 摘要字段。
- 详情接口拆分为基础信息、原文预览、chunk 分页、聊天记录分页。
- 大文本默认只返回预览，用户需要时再加载全文。

**验收标准：**

- 列表接口响应体大小明显下降。
- 大文档知识库详情首屏不再等待全文和全部 chunks。

---

### 4.2 优化 RAG 调用链

**问题：**

单次 RAG 问答可能包含查询改写、问题 embedding、多路检索、图谱实体抽取、rerank、答案生成等多个步骤，其中多步会调用 LLM。调用链越长，p95 延迟和成本越高。

**建议：**

- 查询改写按需开启：短问题、明确问题可跳过。
- 图谱实体抽取按需开启：普通问答先走向量检索，低置信度再补图谱。
- query embedding、query rewrite 结果做短期缓存。
- rerank 只在候选结果分数接近或召回质量不足时触发。

**验收标准：**

- 单次 RAG 平均 LLM 调用次数下降。
- RAG 首 token 时间和完整响应时间下降。
- 答案质量不明显下降。

---

### 4.3 优化图谱检索和兜底检索

**问题：**

图谱检索存在 `ILIKE '%keyword%'` 模糊匹配，普通 B-tree 索引难以生效。向量检索兜底路径会把 chunks 全量取出，在 Python 中逐条计算相似度。

**建议：**

- 图谱实体与来源 chunk 建立明确映射，优先通过 `source_chunk_id` 回查。
- 文本模糊搜索改用 PostgreSQL full-text search 或 trigram 索引。
- 移除或限制 Python 全量相似度兜底；兜底最多处理小规模候选集合。

**验收标准：**

- 大知识库下图谱搜索不再出现长时间扫描。
- 兜底路径不会拉取全量 chunks 到应用内存。

---

### 4.4 前端轮询和流式渲染优化

**问题：**

多个页面通过固定间隔轮询任务状态；RAG 流式输出时每个 chunk 都触发 Markdown + 代码高亮重新渲染。长回答、长报告、多人并发时会增加浏览器主线程和后端接口压力。

**建议：**

- 任务状态优先使用 SSE/WebSocket，或至少统一为轻量 status endpoint。
- 流式回答时先按 50-100ms 批量刷新纯文本，结束后再做完整 Markdown 渲染。
- 长 Markdown 文档使用懒加载或折叠分段渲染。

**验收标准：**

- 长回答流式输出时页面不卡顿。
- 智能下载长报告完成后首屏可快速响应。
- 后端任务状态接口 QPS 明显下降。

---

## 五、P2：持续优化

### 5.1 建立性能指标和基线

建议补齐以下指标：

- API：每个路由的 p50、p95、p99、错误率。
- DB：慢查询、连接池等待时间、向量检索耗时。
- LLM：调用耗时、首 token 时间、重试次数、semaphore 等待时间。
- Worker：每个 stream 的队列长度、pending 数、处理耗时、失败率。
- 前端：bundle 大小、首屏耗时、长任务、Markdown 渲染耗时。

### 5.2 建立回归验证方式

建议固定以下验证动作：

```bash
# 前端构建体积
npm run build

# Redis Stream 状态
redis-cli XINFO STREAM <stream-name>
redis-cli XINFO GROUPS <stream-name>

# 数据库查询计划
EXPLAIN ANALYZE <vector-search-sql>;
```

后续可以补充 k6/Locust 压测脚本，覆盖上传简历、构建知识库、RAG 问答、提交面试评估这几条主路径。

---

## 六、建议执行顺序

1. **第一阶段：查询和后台吞吐地基**
   - 增加 HNSW 索引。
   - 用 `EXPLAIN ANALYZE` 验证向量检索计划。
   - 改造 worker 为可配置多实例并发。

2. **第二阶段：去阻塞**
   - 对象存储、文档解析、Embedding 调用从 async 热路径中拆出。
   - Embedding 支持批量或有界并发。
   - 检查上传和知识库索引期间 API p95。

3. **第三阶段：减少无效数据传输**
   - 列表接口字段裁剪。
   - 知识库详情、简历详情、面试详情拆分页和懒加载。
   - 前端避免一次性渲染全文 Markdown。

4. **第四阶段：降低 RAG 链路成本**
   - 查询改写、图谱检索、rerank 改为按需触发。
   - 增加 query embedding 和改写缓存。
   - 优化图谱搜索和兜底检索。

5. **第五阶段：监控和压测闭环**
   - 建立性能基线。
   - 加入 worker 队列、LLM 等待、DB 慢查询、前端渲染指标。
   - 每次性能改造后记录前后对比。
