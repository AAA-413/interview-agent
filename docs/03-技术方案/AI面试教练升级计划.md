# AI 面试教练升级计划

> 文档日期：2026-05-21
> 配套大纲：[AI面试教练产品升级大纲](./AI面试教练产品升级大纲.md)
> 目标周期：4-8 周完成从“面试工具箱”到“面试教练 MVP”的升级

---

## 一、升级目标

### 1.1 总目标

将当前系统升级为一个面向同学求职准备的 AI 面试教练，帮助用户完成：

1. 明确目标岗位要求
2. 诊断个人短板
3. 生成个性化训练计划
4. 进行真实模拟面试
5. 获得可执行反馈
6. 沉淀错题并持续复训

### 1.2 MVP 定义

MVP 不追求覆盖所有面试场景，第一阶段只聚焦校招/转岗同学，优先打通一个完整闭环：

```text
用户上传简历 + 填写目标岗位
  ↓
系统生成诊断报告和 7 天计划
  ↓
用户完成项目深挖或知识题训练
  ↓
系统给出教练式反馈和优化回答
  ↓
训练结果进入弱点画像和复训任务
```

### 1.3 非目标

短期不优先做：

- 3-5 年以上社招深度面试路线
- 中高级系统设计专项
- 大规模题库运营后台
- 完整付费系统
- 企业招聘端
- 多人协作课堂
- 复杂社群功能
- 全量语音面试

这些可以在 MVP 验证后再进入增长阶段。

说明：短期不做“全量实时语音面试”，但保留轻量语音输入能力。当前已采用 voice-lite 方案：前端录音上传，后端用本地 faster-whisper 转写为文本，再复用现有 DeepSeek 追问和评分链路。选型细节见：[语音识别方案选型](./语音识别方案选型.md)。

## 二、现有能力复用

| 现有模块 | 可复用能力 | 升级使用方式 |
|----------|------------|--------------|
| 简历管理 | 简历解析、评分、项目提取 | 诊断入口和项目深挖素材 |
| 模拟面试 | 出题、追问、评分、历史记录 | 教练式训练主链路 |
| Skill | 岗位方向定义 | 目标岗位画像基础 |
| 知识库 RAG | 文档入库、检索、问答 | 知识补弱和资料转题库 |

| Agent 编排 | 规划、执行、质检、总结 | 训练计划和资料处理自动化 |
| 测试与质量脚本 | Ruff、pytest、前端 build | 持续交付保障 |

## 三、阶段计划

## Phase 1：面试诊断首页

### 目标

让用户进入系统后，第一屏就知道：

- 我当前离目标岗位差什么？
- 面试官最可能追问我什么？
- 今天应该练什么？

### 用户故事

作为校招/转岗同学，我希望上传简历并填写目标岗位后，系统给我一份清晰的诊断报告，而不是让我自己在各个功能里找入口。

### 功能范围

#### 后端

- 新增诊断服务：`InterviewDiagnosisService`
- 输入：
  - `resume_id` 或 `resume_text`
  - `target_role`
  - `target_company`
  - `level`
  - `jd_text`
- 输出：
  - `readiness_score`
  - `weaknesses`
  - `resume_risks`
  - `project_follow_up_questions`
  - `knowledge_gaps`
  - `seven_day_plan`
  - `today_tasks`

#### 前端

- 新增页面：`InterviewDiagnosisPage`
- 页面结构：
  - 目标岗位表单
  - 简历选择/上传入口
  - 诊断结果总览
  - 短板 Top 5
  - 高风险追问
  - 今日训练任务
  - 进入训练按钮

#### 数据

建议先不新增复杂表结构，第一版可以复用面试记录和简历分析结果。若需要持久化，可新增：

- `interview_diagnoses`
- `interview_diagnosis_items`

### 验收标准

- 用户可以从首页完成一次诊断。
- 诊断报告可以直接跳转到项目深挖或模拟面试。
- 诊断结果不少于 3 个短板、3 个风险追问、1 个 7 天计划。
- 诊断接口有基础单测。

### 预估周期

1-2 周。

## Phase 2：项目深挖训练

### 目标

解决学生最常见的问题：简历项目写了，但讲不深，经不起追问。

当前优先做第一版轻量闭环：不新增数据库表，先从简历 profile 中选择项目，生成连续追问、回答框架、加分信号和扣分雷区。
项目深挖不是孤立页面，生成追问后会进入原有模拟面试会话，复用答题、追问、历史记录和报告链路。

### 用户故事

作为后端/前端/AI 方向同学，我希望系统根据我的简历项目模拟面试官连续追问，并告诉我项目回答哪里不真实、哪里不够深入。

### 功能范围

#### 后端

- 新增项目深挖训练模式：
  - 输入项目名称或从简历中选择项目
  - 生成项目追问题
  - 支持真实性、技术深度、指标量化、方案取舍四类追问
- 新增接口：`POST /api/interview/project-drill`
- 扩展原有会话创建：`POST /api/interview/sessions`
  - `interview_mode=project_drill`
  - `skill_id=project-drill`
  - 生成的题目统一标记为 `question_type=project`
- 第一版输出：
  - 选中的核心项目
  - 项目风险总结
  - 2 分钟暖场题
  - 连续追问题
  - 每题回答框架、加分信号、扣分雷区
  - 练习清单
- 复用原有项目题 LLM 评估维度：
  - `authenticity`
  - `technical_depth`
  - `depth`
  - `expression`
- 项目题反馈按教练式格式输出：
  - 面试官判断
  - 当前风险点
  - 80 分改法
  - 下一步追问

#### 前端

- 新增页面：`ProjectDrillPage`
- 在诊断结果中把主行动升级为“项目深挖训练”。
- 页面展示：
  - 高风险问题
  - 建议补充素材
  - 连续追问题
  - 回答框架
  - 加分信号和扣分雷区

### 输出格式

每道项目题反馈应包含：

```text
面试官判断：
当前回答问题：
缺失细节：
推荐回答结构：
优化版回答：
下一道追问：
```

### 验收标准

- 能从简历项目生成至少 5 道深挖题。
- 能对项目回答给出真实性和技术深度评分。
- 能生成一版可直接练习的优化回答。
- 项目深挖结果进入面试历史。

### 预估周期

1-2 周。

---

## Phase 3：教练式反馈

### 目标

把“评分报告”升级为“下一步怎么改”。

### 用户故事

作为学生，我不只想知道自己得了 60 分，我还想知道如果我要答到 80 分或 90 分，应该怎么补。

### 功能范围

#### 后端

- 扩展 `QuestionEvaluationDTO`
- 新增字段建议：
  - `interviewer_judgement`
  - `answer_issues`
  - `missing_points`
  - `answer_framework`
  - `answer_60`
  - `answer_80`
  - `answer_90`
  - `next_practice_question`

#### 前端

- 回答分析页面新增“优化回答”区域。
- 支持对比：
  - 我的原回答
  - 80 分回答
  - 90 分回答

### 验收标准

- 每次评估至少输出 1 条可执行修改建议。
- 至少给出 80 分优化回答。
- 用户能基于同一题再次练习。

### 预估周期

1 周。

---

## Phase 4：弱点画像与错题复训

### 目标

让用户持续知道自己哪些地方没掌握，并自动生成复训任务。

### 用户故事

作为持续备考的同学，我希望系统自动记录我的错题和薄弱知识点，每天告诉我该复习什么。

### 功能范围

#### 后端

- 新增弱点标签体系：
  - 知识原理
  - 项目经验
  - 系统设计
  - 表达结构
  - 代码实现
  - 真实可信度
- 新增错题/弱点持久化：
  - `weakness_items`
  - `practice_tasks`
- 自动从低分评估中生成复训任务。

#### 前端

- 新增“我的弱点”页面。
- 展示：
  - 弱点雷达图
  - 错题列表
  - 今日复训
  - 最近提升趋势

### 验收标准

- 低分题能自动进入错题本。
- 用户可以重新练习错题。
- 同一弱点多次训练后能看到趋势变化。

### 预估周期

1-2 周。

## Phase 5：知识库能力产品化

### 目标

把 RAG、GraphRAG、智能下载包装成学生能直接理解的学习功能。

### 功能形态

| 底层能力 | 产品化入口 |
|----------|------------|
| 智能下载 | 面经整理器 |
| 知识库上传 | 资料转题库 |
| RAG 问答 | 知识补弱助手 |
| GraphRAG | 关联知识点地图 |
| 文档分块 | 复习卡片 |

### 首批场景

1. 博客 URL 转面试题
2. JD 转训练计划
3. 面经文本转错题清单
4. 项目文档转深挖问题

### 验收标准

- 用户不用理解“知识库”也能完成资料转训练题。
- 转换结果能直接进入训练计划。
- 每份资料至少生成题目、知识卡片和复习建议。

### 预估周期

1-2 周。

## 四、数据模型草案

### 4.1 诊断报告

```python
class InterviewDiagnosis:
    id: int
    user_id: int
    resume_id: int | None
    target_role: str
    target_company: str | None
    level: str | None
    jd_text: str | None
    readiness_score: int
    summary: str
    weaknesses: list[dict]
    resume_risks: list[dict]
    knowledge_gaps: list[dict]
    seven_day_plan: list[dict]
    today_tasks: list[dict]
```

### 4.2 弱点项

```python
class WeaknessItem:
    id: int
    user_id: int
    source_type: str  # interview | diagnosis | resume
    source_id: str
    category: str
    label: str
    severity: int
    evidence: str
    suggestion: str
    status: str  # open | practicing | improved | resolved
```

### 4.3 复训任务

```python
class PracticeTask:
    id: int
    user_id: int
    weakness_id: int | None
    task_type: str  # project_deep_dive | knowledge | mock | rewrite
    title: str
    prompt: str
    due_date: date | None
    status: str  # pending | done | skipped
```

## 五、关键提示词方向

### 5.1 诊断 Prompt

输入：

- 简历摘要
- 项目列表
- 技术栈
- 目标岗位/JD
- 历史面试表现（可选）

输出：

- 岗位匹配度
- 风险点
- 知识缺口
- 项目追问
- 训练计划

要求：

- 不泛泛建议
- 每条短板必须有证据
- 每条任务必须可执行

### 5.2 项目深挖 Prompt

重点问：

- 为什么做
- 怎么设计
- 为什么这么选
- 遇到什么问题
- 指标是多少
- 如何证明有效
- 如果重做会怎么改

### 5.3 教练反馈 Prompt

固定输出：

- 面试官判断
- 当前回答短板
- 推荐回答框架
- 高分回答版本
- 下一题

## 六、技术实施顺序

### Sprint 1：诊断闭环

1. 新增诊断 API。
2. 新增诊断页面。
3. 打通简历选择和岗位输入。
4. 输出短板、风险追问、训练计划。
5. 添加基础测试。

### Sprint 2：项目深挖

1. 从简历 profile 中选择项目。
2. 生成项目追问题。
3. 扩展评估维度。
4. 前端展示项目深挖反馈。

### Sprint 3：教练反馈

1. 扩展评估 DTO。
2. 增加优化回答生成。
3. 前端展示回答对比。
4. 支持同题再练。

### Sprint 4：弱点复训

1. 新增弱点模型。
2. 低分题自动生成弱点。
3. 新增错题本页面。
4. 新增今日复训任务。

### Sprint 5：资料转训练

1. 智能下载入口改造成面经/博客转题。
2. 资料结果进入训练计划。
3. 支持知识卡片和复习建议。

## 七、验收指标

### 产品指标

- 诊断完成率 >= 60%
- 诊断后训练点击率 >= 50%
- 模拟面试完成率 >= 40%
- 同一题二次回答平均分提升 >= 15 分
- 7 日内完成 3 次训练用户占比 >= 30%

### 技术指标

- `./scripts/quality_check.sh` 稳定通过
- 关键 API 有基础单测
- 诊断接口 P95 < 60 秒
- 单次训练评估 P95 < 45 秒
- LLM 调用失败有明确降级提示

## 八、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 诊断结果泛泛 | 用户不信任 | 强制每条建议绑定简历/JD 证据 |
| LLM 输出不稳定 | 页面渲染失败 | Pydantic alias + 结构化输出重试 |
| 训练链路过长 | 用户中途退出 | 首页只给今日 1-3 个任务 |
| 功能入口太多 | 用户迷路 | 以诊断报告作为统一入口 |
| 评估等待时间长 | 用户流失 | 流式状态、阶段进度、后台任务 |
| 错题沉淀过重 | 用户不复习 | 自动生成每日轻量复训 |

## 九、下一步建议

下一步最建议先做 Sprint 1：

> 新增“面试诊断首页”，把简历、目标岗位、短板、训练任务串成一个主路径。

这是最能改变产品心智的一步。完成后，系统会从“有很多功能”变成“我知道你该怎么准备”。

## 十、第一阶段落地口径

当前已按 Sprint 1 进入实现，第一版采取“稳定、可解释、可行动”的方案：

1. 第一阶段核心用户已确定为校招/转岗同学，不兼顾 3-5 年以上社招深度路线。
2. 诊断分数定义为“面试准备度”，不是录用概率，也不是单纯简历分。
3. 诊断优先复用已有简历解析结果，不先依赖 LLM 黑盒生成，保证建议能追溯到简历评分、项目画像和目标 JD。
4. 输出重点不是泛泛建议，而是三类可执行内容：关键薄弱项、简历追问风险、今日训练任务。
5. 首页入口调整为“面试诊断”，让产品主路径从功能列表变成准备路径。
6. 第一版不新增数据库表，先跑通体验；后续再沉淀弱点、训练记录和复训计划。

### 需要继续讨论的关键问题

1. 诊断口径：分数要偏保守制造行动感，还是偏鼓励减少焦虑？
2. 今日任务粒度：给 3 个任务更聚焦，还是给更多任务让学生自己选择？
3. 训练闭环：诊断后的主按钮应该进入模拟面试，还是进入“项目深挖”专项训练？
4. 商业化切入：免费诊断给多少深度，付费点放在项目追问、答案优化还是 7 天陪练？
