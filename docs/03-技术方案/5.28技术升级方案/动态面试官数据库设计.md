# 动态面试官数据库设计

文档日期：2026-05-28

## 1. 设计结论

由于当前基本没有历史面试数据负担，下一阶段不建议继续围绕旧的 `questions_json + interview_answers.question_index` 扩展。

新主链路采用：

```text
interview_sessions
  -> interview_topics
      -> interview_turns
```

核心原则：

- `interview_sessions` 只承载会话级状态和最终汇总。
- `interview_topics` 承载面试主题、分类、证据、去重和 topic 级评分。
- `interview_turns` 承载每一次主问、追问、重答和当轮决策。
- 旧 `interview_answers` 可先保留，但不再扩展为动态面试主链路。

## 2. 现有结构问题

当前模型主要是：

```text
interview_sessions.questions_json
interview_answers.question_index
interview_answers.question
interview_answers.user_answer
interview_answers.score
```

它适合“一次生成 N 道题，再逐题提交答案”，但不适合动态面试官：

- 无法表达一个 topic 下多轮追问。
- 同题重答和追问都只能伪装成新的 question_index。
- `category` 是自由字符串，导致统计口径不稳定。
- 缺少 `topic_key/evidence_hash`，跨 session 去重困难。
- `question_type`、`turn_type`、`decision_action` 没有稳定枚举。

## 3. 枚举定义

这些枚举应在后端模型中固化，不能依赖 prompt 自觉输出。

### 3.1 InterviewEngineType

```text
STATIC
DYNAMIC
```

说明：

- `STATIC`：旧静态题目模式，后续逐步弱化。
- `DYNAMIC`：新 topic/turn 模式。

### 3.2 InterviewMode

```text
STRICT
COACH
```

说明：

- `STRICT`：严厉技术面试官，用于压力测试和真实性验证。
- `COACH`：教练型技术面试官，用于提示、重答和提升闭环。

### 3.3 DynamicSessionStatus

```text
PLANNING
INTERVIEWING
COMPLETED
ABANDONED
FAILED
```

说明：

- `PLANNING`：正在生成 topic plan。
- `INTERVIEWING`：面试进行中。
- `COMPLETED`：用户完成并生成报告。
- `ABANDONED`：用户中途退出或超时。
- `FAILED`：计划生成或核心流程失败。

### 3.4 InterviewQuestionType

```text
PROJECT
KNOWLEDGE
SYSTEM_DESIGN
```

说明：

- `PROJECT`：必须绑定简历证据。
- `KNOWLEDGE`：通用知识题，不要求简历证据。
- `SYSTEM_DESIGN`：假设场景题，必须明确是假设/设计/优化/排障。

### 3.5 TopicStatus

```text
PENDING
ACTIVE
COMPLETED
SKIPPED
FAILED
```

### 3.6 TurnType

```text
MAIN
FOLLOW_UP
COACH_RETRY
```

说明：

- `MAIN`：topic 的主问题。
- `FOLLOW_UP`：严厉模式或必要追问。
- `COACH_RETRY`：教练模式中提示后的同题重答。

### 3.7 DecisionAction

```text
FOLLOW_UP
COACH_RETRY
NEXT_TOPIC
END
```

说明：

- `FOLLOW_UP`：继续追问。
- `COACH_RETRY`：给提示并让用户重答。
- `NEXT_TOPIC`：当前 topic 结束，进入下一 topic。
- `END`：结束整场面试。

## 4. 表结构设计

### 4.1 interview_sessions

建议在现有 `interview_sessions` 上演进，而不是新建 `dynamic_sessions`，避免未来历史、训练计划和报告入口分裂。

新增或调整字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `engine_type` | enum/string | `STATIC/DYNAMIC` |
| `interview_mode` | enum/string | `STRICT/COACH` |
| `target_role` | string(120) | 目标岗位 |
| `target_company` | string(120), nullable | 目标公司 |
| `level` | string(40), nullable | 候选人等级 |
| `jd_text` | text, nullable | 用户输入 JD |
| `current_topic_id` | bigint, nullable | 当前 topic |
| `project_score` | int, nullable | 项目题分项 |
| `knowledge_score` | int, nullable | 知识题分项 |
| `system_design_score` | int, nullable | 系统设计分项 |
| `plan_summary_json` | text/json, nullable | 面试计划摘要 |
| `final_report_json` | text/json, nullable | 动态报告完整结构 |

保留字段：

- `session_id`
- `user_id`
- `resume_id`
- `skill_id`
- `difficulty`
- `status`
- `overall_score`
- `overall_feedback`
- `created_at`
- `completed_at`

逐步弱化字段：

- `questions_json`
- `current_question_index`
- `total_questions`
- `reference_answers_json`

推荐索引：

```text
idx_interview_session_user_created(user_id, created_at)
idx_interview_session_user_mode_created(user_id, interview_mode, created_at)
idx_interview_session_resume_created(resume_id, created_at)
idx_interview_session_engine_status_created(engine_type, status, created_at)
```

### 4.2 interview_topics

新表。它是动态面试官的核心表，必须结构化，不能只放 JSON。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint pk | 主键 |
| `session_id` | bigint fk | 关联 `interview_sessions.id` |
| `user_id` | bigint fk | 冗余用户 ID，便于查询和隔离 |
| `resume_id` | bigint, nullable | 关联简历 |
| `topic_key` | string(120) | 稳定主题 key |
| `topic_title` | string(200) | 中文展示标题 |
| `skill_key` | string(80) | 能力 key，如 `rag`、`agent`、`mcp` |
| `question_type` | enum/string | `PROJECT/KNOWLEDGE/SYSTEM_DESIGN` |
| `source_type` | string(40) | `resume/jd/skill/history/mixed` |
| `evidence_snippet` | text, nullable | 简历或 JD 证据片段 |
| `evidence_hash` | string(64), nullable | 证据片段 hash，用于去重 |
| `main_question` | text | 主问题 |
| `topic_order` | int | topic 顺序 |
| `status` | enum/string | topic 状态 |
| `max_turns` | int | 最大 turn 数 |
| `turn_count` | int | 已完成 turn 数 |
| `best_score` | int, nullable | topic 内最高分 |
| `final_score` | int, nullable | topic 最终分 |
| `followup_goals_json` | text/json | 追问目标 |
| `exit_criteria_json` | text/json | 退出条件 |
| `rubric_json` | text/json | topic 评分规则 |
| `created_at` | datetime | 创建时间 |
| `completed_at` | datetime, nullable | 完成时间 |

唯一约束：

```text
uk_interview_topic_session_order(session_id, topic_order)
```

推荐索引：

```text
idx_interview_topic_session_order(session_id, topic_order)
idx_interview_topic_user_created(user_id, created_at)
idx_interview_topic_user_topic_created(user_id, topic_key, created_at)
idx_interview_topic_user_type_created(user_id, question_type, created_at)
idx_interview_topic_user_skill_created(user_id, skill_key, created_at)
idx_interview_topic_evidence_hash(user_id, evidence_hash)
```

### 4.3 interview_turns

新表。每一次主问、追问、重答都是一个 turn。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint pk | 主键 |
| `session_id` | bigint fk | 关联会话 |
| `topic_id` | bigint fk | 关联 topic |
| `user_id` | bigint fk | 用户 ID |
| `turn_type` | enum/string | `MAIN/FOLLOW_UP/COACH_RETRY` |
| `turn_order` | int | topic 内顺序 |
| `question` | text | 当前问题 |
| `answer` | text, nullable | 用户回答 |
| `ability_score` | int, nullable | 统一能力分 |
| `decision_action` | enum/string, nullable | 下一步动作 |
| `feedback` | text, nullable | 当轮反馈 |
| `evaluation_json` | text/json, nullable | 完整评分结果 |
| `signals_json` | text/json, nullable | 强项、缺口、疑点 |
| `decision_json` | text/json, nullable | 决策原因和下一问 |
| `coach_hint_json` | text/json, nullable | 教练提示 |
| `created_at` | datetime | 问题生成时间 |
| `answered_at` | datetime, nullable | 回答时间 |

唯一约束：

```text
uk_interview_turn_topic_order(topic_id, turn_order)
```

推荐索引：

```text
idx_interview_turn_session_created(session_id, created_at)
idx_interview_turn_topic_order(topic_id, turn_order)
idx_interview_turn_user_created(user_id, created_at)
idx_interview_turn_user_type_created(user_id, turn_type, created_at)
idx_interview_turn_decision_action(user_id, decision_action, created_at)
```

## 5. 结构化列与 JSON 边界

### 5.1 必须结构化的字段

这些字段未来会用于查询、统计、趋势、去重和训练计划，不能只放 JSON：

```text
user_id
session_id
resume_id
topic_id
topic_key
skill_key
question_type
interview_mode
engine_type
turn_type
ability_score
decision_action
evidence_hash
status
created_at
answered_at
completed_at
```

### 5.2 可以先放 JSON 的字段

这些字段结构会持续迭代，第一版可以 JSON：

```text
followup_goals
exit_criteria
rubric
signals
dimension_scores
covered_points
missed_points
coach_hint
decision_detail
final_report
```

边界原则：

- 会被频繁过滤、排序、聚合的字段必须结构化。
- 主要用于展示、解释和 LLM 上下文的字段可以 JSON。

## 6. 状态流转

### 6.1 Session 状态

```text
PLANNING
  -> INTERVIEWING
  -> COMPLETED

PLANNING
  -> FAILED

INTERVIEWING
  -> ABANDONED
```

### 6.2 Topic 状态

```text
PENDING
  -> ACTIVE
  -> COMPLETED

PENDING/ACTIVE
  -> SKIPPED

ACTIVE
  -> FAILED
```

同一 session 同一时间只应有一个 `ACTIVE` topic。

### 6.3 Turn 状态

`interview_turns` 不单独设置 status，使用时间字段判断：

```text
created_at 有值，answered_at 为空：待回答
answered_at 有值：已回答
decision_action 有值：已决策下一步
```

第一版可以不允许同一 topic 下存在多个未回答 turn。

## 7. 模式策略与数据落点

### 7.1 严厉模式

数据表现：

```text
MAIN -> FOLLOW_UP -> FOLLOW_UP -> NEXT_TOPIC
```

规则：

- 每个 topic 最多 3 个 turn。
- `coach_hint_json` 为空。
- `decision_action` 主要为 `FOLLOW_UP/NEXT_TOPIC/END`。
- 追问优先覆盖职责、细节、指标、异常、权衡。

### 7.2 教练模式

数据表现：

```text
MAIN -> COACH_RETRY -> COACH_RETRY -> NEXT_TOPIC
```

规则：

- 每个 topic 最多 1 个首次回答 + 2 次重答。
- `coach_hint_json` 必填。
- `decision_action` 主要为 `COACH_RETRY/NEXT_TOPIC/END`。
- 重答后计算 `initial_score/retry_score/score_delta`，可以从 turn 记录聚合得到，不一定单独建表。

## 8. Topic 去重模型

每次创建 topic 必须保存：

```text
topic_key
skill_key
question_type
evidence_hash
created_at
final_score
```

生成新面试计划时读取：

```text
当前用户最近 2 次或最近 7 天的 interview_topics
```

去重规则：

- 同一 `topic_key` 最近 2 次普通面试已出现，默认降权或排除。
- 同一 `evidence_hash + question_type` 已出现，避免换句话重复问同一证据。
- 低分 topic 可进入复练，但必须标记为 `COACH_RETRY` 或同题再练入口，而不是伪装成新题。
- 核心能力可重复，但必须换 `topic_key` 或换追问角度。

## 9. 报告汇总逻辑

动态面试报告不应只按题号汇总，而应按 topic 汇总。

### 9.1 Topic 分数

建议：

```text
topic.final_score = 当前 topic 最后一次有效回答分
topic.best_score = 当前 topic 所有回答最高分
```

严厉模式更看 `final_score`。

教练模式同时展示：

```text
initial_score
best_score
score_delta
```

### 9.2 分项分数

按 `question_type` 分开算：

```text
project_score = PROJECT topics 平均分
knowledge_score = KNOWLEDGE topics 平均分
system_design_score = SYSTEM_DESIGN topics 平均分
```

综合分建议：

```text
overall_score = project_score * 0.5 + knowledge_score * 0.3 + system_design_score * 0.2
```

如果某一类本场没有覆盖，则按实际覆盖类型重新归一化，不要把缺失类按 0 分计算。

### 9.3 报告结构

`final_report_json` 建议包含：

```json
{
  "overall_score": 76,
  "project_score": 80,
  "knowledge_score": 72,
  "system_design_score": 68,
  "topic_summaries": [],
  "strengths": [],
  "risks": [],
  "training_tasks": [],
  "retry_deltas": []
}
```

## 10. API 草案

### 10.1 创建动态面试

```http
POST /api/interview/dynamic-sessions
```

请求：

```json
{
  "resume_id": 16,
  "target_role": "AI 开发实习生",
  "jd_text": "...",
  "mode": "COACH",
  "topic_count": 4
}
```

响应：

```json
{
  "session_id": "abc",
  "status": "INTERVIEWING",
  "current_topic": {},
  "current_turn": {
    "turn_id": 1,
    "question": "..."
  }
}
```

### 10.2 提交回答

```http
POST /api/interview/dynamic-sessions/{session_id}/turns/{turn_id}/answer
```

响应：

```json
{
  "evaluation": {
    "ability_score": 72,
    "feedback": "...",
    "signals": {}
  },
  "decision": {
    "action": "COACH_RETRY",
    "reason": "...",
    "hint": {},
    "next_question": "..."
  },
  "next_turn": {}
}
```

### 10.3 获取详情

```http
GET /api/interview/dynamic-sessions/{session_id}
```

返回 session、topics、turns 和当前进度。

### 10.4 完成面试

```http
POST /api/interview/dynamic-sessions/{session_id}/complete
```

触发 topic 汇总和最终报告生成。

## 11. 旧表处理策略

由于当前基本没有旧数据负担，推荐策略：

1. 保留 `interview_answers`，短期不删除，避免 import、测试和旧页面连锁改动。
2. 新动态接口不再写 `interview_answers`。
3. 旧静态接口可以继续写旧表，但不再新增复杂能力。
4. 报告、趋势和训练计划逐步切换到 `interview_topics/interview_turns`。
5. 新链路稳定后，再决定是否删除旧字段和旧表。

不建议：

- 把动态追问继续塞进 `questions_json`。
- 把重答伪装成新的 `question_index`。
- 继续让 `category` 自由输出中文或英文混合值。

## 12. Alembic 实施建议

建议拆成两次迁移，降低风险：

### 12.1 迁移 A：会话表扩展和枚举

- 新增 enum 或 string check。
- 给 `interview_sessions` 增加动态面试字段。
- 增加必要索引。

### 12.2 迁移 B：新增 topic/turn 表

- 创建 `interview_topics`。
- 创建 `interview_turns`。
- 创建索引和唯一约束。

如果使用 PostgreSQL enum，注意 downgrade 要谨慎处理 enum 类型删除；如果当前项目迁移还不稳定，第一版也可以先用 `String + 应用层枚举校验`，等模型稳定后再收紧 DB check。

## 13. 第一版实现切片

建议第一刀只做教练模式：

```text
4 个 topic
  - 2 个 PROJECT
  - 1 个 KNOWLEDGE
  - 1 个 SYSTEM_DESIGN

每个 topic:
  MAIN -> COACH_RETRY -> COACH_RETRY -> NEXT_TOPIC
```

最小验收：

1. 能创建动态 session。
2. 能生成 topic plan。
3. 能返回第一个 main turn。
4. 用户提交回答后能生成评分、signals、coach hint 和下一 turn。
5. 能完成一个 topic 的首次回答、提示、重答、对比。
6. 最终能按 topic 汇总报告。
