- 简历上传与解析是否稳定。
- JD 输入后，题目是否贴合岗位要求。
- 题目是否真实引用简历内容，避免无依据扩写。
- 多次生成时是否有足够覆盖面和差异性。
- 题目结构是否适合真实模拟面试。

## 6. 主要问题

### 6.1 问题过密

不少题目包含 3 到 4 个子问题，例如“解释架构 + 说明指标 + 处理异常 + 如何评估”。这会导致候选人难以组织回答，也不利于系统后续评分。

建议：生成时约束为“一个主问题 + 一个核心追问”，剩余追问放到 follow-up 阶段。

### 6.2 多轮生成重复度偏高

三轮中反复出现：

- 智能下载多 Agent / PlanningAgent
- RAG 多通道检索
- MCP 工具集成

这些主题本身重要，但连续多轮基准里重复较多。若用户多次创建面试，应引入 session history 去重或 topic coverage 策略。

建议：题目生成增加“最近 N 次面试已覆盖主题”输入，按 topic_key 做降权。

### 6.3 术语归一化与证据匹配需要更稳

本次初始核对时按 `SummaryAgent` 做精确匹配，未命中文本；后续人工复核 PDF 发现，简历中实际写成了 `SummaryAgen`，少了末尾的 `t`。因此 Run 3 的 `SummaryAgent 整合多源内容入库` 不应判定为无依据扩写，更准确地说是模型将简历中的疑似拼写错误归一化成了常见组件名。

建议：项目题仍需绑定证据片段，但质量检查不能只靠完全一致的字符串匹配。需要支持大小写、空格、连字符、英文单复数和轻微拼写错误的归一化匹配；同时，简历分析可以把 `SummaryAgen -> SummaryAgent` 作为简历优化建议提示给用户。

### 6.4 标签口径不统一

部分题目的 category/type 表达不稳定，例如：

- `AGENT_BASIS`
- `Agent 基础`
- `PROJECT_EXPERIENCE`
- `项目经历`
- 部分 project 题 category 为空

这会影响趋势统计、能力雷达图、评分校准和训练计划生成。

建议：统一使用内部枚举 key，再在前端映射中文展示。

### 6.5 “项目经历题”和“系统设计题”边界需要更清楚

例如“长期记忆 AI Agent 如何设计”更像系统设计题，不应简单归入项目经历，除非简历明确写了长期记忆实现。

建议：增加 `scenario` 或 `system_design` 类型，和 `project`、`knowledge` 分开统计。

### 6.6 生成耗时偏高

8 道题生成耗时约 `22s`、`38s`、`48s`，对于正式产品偏慢。演示模式可接受，但真实用户会明显等待。

建议：

- 前端提供明确的生成中状态。
- 题目生成异步化，先创建 session，再轮询题目状态。
- 对简历结构化摘要、项目标签、JD embedding 做缓存。
- 控制单次 LLM 调用数量，减少不必要的串行调用。

### 6.7 上传去重存在跨用户问题

第一次用新账号上传同一 PDF 时，接口返回“简历不存在或已被删除”。原因是上传服务按全局 `file_hash` 去重，命中了其他用户已有简历，但后续详情查询又按当前用户过滤，导致跨用户不可见。

本次为了继续基准，用相同 PDF 内容追加换行后重新上传，绕过了 hash 冲突。

建议：简历去重必须按 `user_id + file_hash` 作用域处理；或者命中全局文件时创建当前用户自己的 resume 记录。

## 7. 下一步质量基准建议

优先修复：

1. 项目题证据绑定：每道项目题保存 `evidence_snippet`，禁止把无证据术语写成候选人经历。
2. 题目密度控制：主问题和追问拆分，避免一道题承载过多评分点。
3. topic 去重：同一用户多次生成时降低已覆盖主题权重。
4. category 枚举统一：修复趋势统计和训练计划的数据基础。
5. 上传去重按用户隔离：修复真实用户上传同一公开简历或重复测试简历时的失败。

后续可做：

- 建立 5 到 10 份不同方向简历的固定基准集。
- 每次调整题目 prompt 或生成逻辑后，跑相同基准集并记录 JD 贴合度、简历贴合度、重复率、无依据术语率和生成耗时。
- 将“知识题正确性”和“项目题真实性”拆成两个质量指标，分别评估。
