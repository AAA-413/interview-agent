# 动态面试官升级计划

文档日期：2026-05-28

## 1. 背景

当前模拟面试已经能基于简历和 JD 生成较高质量的问题，但从质量基准看，系统仍偏向“题库生成器”：

- 创建会话时一次性生成固定题目。
- 单题常包含多个子问题，候选人回答压力大，评分点混杂。
- 多轮面试容易重复围绕 RAG、多 Agent、MCP 等高频主题。
- `project / knowledge / system_design` 边界不够稳定。
- 生成 8 道题耗时约 22-48 秒，正式产品体验偏慢。
- 质量基准目前主要评估出题质量，还没有覆盖回答评分、追问决策和教练提升。

因此下一阶段目标不是继续堆更多题，而是把模拟面试升级为“受控动态面试官”。

## 2. 产品定位

动态面试官不是自由聊天机器人，也不是一次性题库生成器。

它应该是：

```text
先规划面试主题
  -> 提出一个清晰主问题
  -> 根据用户回答评估信号
  -> 决定追问、提示、重答、换题或结束
  -> 最终沉淀报告和训练计划
```

第一版坚持“受控动态”：

- 主题是预规划的。
- 追问是动态生成的。
- 评分是结构化的。
- 模式策略是可测试的。
- 不做完全自由聊天式面试。

## 3. 两种模式

系统支持两种可选模式：

- 严厉技术面试官：用于压力测试和真实性验证。
- 教练型技术面试官：用于训练表达和同题提升。

核心原则：

**能力评分标准统一，面试策略不同。**

同一个回答不应因为模式不同得到完全不同的能力分；模式影响的是追问方式、反馈时机、是否给提示、是否允许重答。

| 模式 | 目标 | 策略 | 反馈 | 适合场景 |
| --- | --- | --- | --- | --- |
| 严厉技术面试官 | 测水平、验真实性 | 连续追问职责、细节、指标、异常、权衡 | 每题后少反馈，最终集中反馈 | 面试前压力测试 |
| 教练型技术面试官 | 练提升、补表达 | 诊断问题、给结构提示、允许同题重答 | 每题后即时反馈 | 日常训练、同题再练 |

## 4. 核心流程

### 4.1 创建面试

```text
用户选择简历、JD、岗位方向、面试模式
  -> 系统生成 InterviewPlan
  -> 返回第一个 topic 的 main_question
```

第一版不再把“生成 8 道完整题目”作为核心，而是生成 `InterviewPlan`：

- 4-5 个主题 topic。
- 每个 topic 一个主问题。
- 每个 topic 绑定证据片段或知识点来源。
- 每个 topic 配置追问目标、退出条件和最大 turn 数。

### 4.2 用户回答

```text
用户回答当前问题
  -> evaluate_answer 统一评分
  -> extract_signals 提取强项、缺口、疑点
  -> policy 决策下一步
  -> 返回追问、提示、重答或下一题
```

### 4.3 严厉模式

每个 topic 最多：

```text
主问题 -> 追问 1 -> 追问 2 -> 换题
```

策略：

- 不给答案提示。
- 不允许同题重答。
- 优先追问个人职责、真实实现、指标口径、异常处理和技术取舍。
- 如果回答明显空泛，追问实现细节。
- 如果回答较强，追问边界条件和权衡。

### 4.4 教练模式

每个 topic 最多：

```text
主问题 -> 首次回答 -> 诊断 -> 结构提示 -> 同题重答 -> 对比反馈 -> 换题
```

策略：

- 允许提示后重答。
- 用户可选择继续重答或进入下一题。
- 每个 topic 最多重答 2 次，避免无限循环。
- 教练提示只给结构和方向，不直接代答。

示例提示：

```text
你刚才讲到了 Cross-Encoder，但还缺少“为什么用它”和“怎么证明有效”。
建议按 背景 -> 方案 -> 个人职责 -> 指标 -> 权衡 重新组织。
```

不应直接输出完整标准答案让用户照抄。

## 6. 分类口径

第一版强制三类：

| 类型 | 定义 | 证据要求 | 示例 |
| --- | --- | --- | --- |
| `project` | 问候选人简历里真实做过的项目 | 必须绑定 `evidence_snippet` | “你简历里提到 Redis Streams 异步任务流水线...” |
| `knowledge` | 问通用概念、原理、框架能力 | 不要求简历证据，可绑定 skill/JD | “Function Calling 的基本流程是什么？” |
| `system_design` | 给定假设场景，让候选人设计、排障或优化 | 需明确是假设题 | “如果 Cross-Encoder 延迟过高，你会怎么优化？” |

约束：

- `project` 题不能把未出现在简历或 JD 中的内容写成候选人已经做过。
- `system_design` 题必须出现“如果/假设/让你设计/如何优化”等场景表达。
- 内部统一存枚举 key，前端只负责中文展示。

## 7. 多轮去重策略

每个 topic 入库时保存：

- `topic_key`
- `skill_key`
- `question_type`
- `evidence_hash`
- `asked_at`
- `score`
- `mode`

生成新计划时读取最近 N 次面试历史：

- 硬规则：最近 2 次已问过的 `topic_key` 默认不再进入普通新面试。
- 软规则：RAG、Agent、MCP 等核心能力可以重复，但必须换角度。
- 复练规则：低分 topic 可以进入“同题再练”，但 UI 必须明确标记为复练。
- 覆盖规则：一次面试尽量覆盖 `project / knowledge / system_design` 和不同 `skill_key`。

## 8. 生成耗时优化

当前创建 8 道题耗时约 22-48 秒。动态面试官应拆成两层：

### 8.1 简历结构化缓存

上传或分析简历时生成：

- `project_cards`
- `skill_graph`
- `risk_points`
- `topic_candidates`
- `evidence_snippets`

这部分可以异步完成并缓存。

### 8.2 面试编排

创建面试时只做：

- 选择 topic。
- 生成主问题。
- 生成 followup goals。
- 生成第一题。

后续追问在用户回答后按需生成。

目标：

- 首题可在 5-15 秒内返回。
- 如果 LLM 慢，先创建 session，前端显示生成状态并轮询。
- 不要求一次生成所有追问文本，只生成追问目标。

## 9. API 草案

### 9.1 创建动态面试

```http
POST /api/interview/dynamic-sessions
```

请求：

```json
{
  "resume_id": 16,
  "target_role": "AI 开发实习生",
  "jd_text": "...",
  "mode": "strict",
  "topic_count": 5
}
```

响应：

```json
{
  "session_id": "session_id",
  "status": "interviewing",
  "current_topic": {...},
  "current_turn": {
    "turn_id": "turn_id",
    "question": "..."
  }
}
```

### 9.2 提交回答并获取下一步

```http
POST /api/interview/dynamic-sessions/{session_id}/turns/{turn_id}/answer
```

响应：

```json
{
  "evaluation": {
    "ability_score": 72,
    "feedback": "...",
    "signals": {...}
  },
  "decision": {
    "action": "follow_up",
    "reason": "...",
    "next_question": "..."
  },
  "next_turn": {...},
  "topic_progress": {...}
}
```

### 9.3 教练模式重答

教练模式不需要单独接口，仍复用提交回答接口；通过 `decision.action = coach_retry` 返回提示和同题重答入口。

## 10. 服务拆分

建议新增或演进以下服务：

```text
InterviewPlanService
  负责生成 topic plan、topic 去重和证据绑定。

AnswerEvaluationService
  负责统一能力评分，不感知 strict/coach 风格。

SignalExtractionService
  负责提取强项、缺口、疑点和追问依据。

InterviewPolicy
  负责根据 mode、topic 状态、signals 决策下一步。

StrictInterviewPolicy
  严厉模式策略。

CoachInterviewPolicy
  教练模式策略。

DynamicQuestionService
  根据 policy 决策生成下一问或提示。
```

重要边界：

- 评分服务不应混入模式偏好。
- policy 不直接打分，只消费评分和 signals。
- question service 不决定是否追问，只负责把决策变成自然语言问题。

## 11. MVP 实施阶段

### Phase 1：数据结构与兼容层

目标：不破坏现有模拟面试，先补动态面试所需结构。

- 新增 `interview_mode`。
- 新增 topic/turn 内部 DTO。
- 当前静态题也可以映射成 topic + main turn。
- 保留旧接口，新增动态接口。

验收：

- 原有模拟面试不受影响。
- 动态会话能创建 session、topic、首个 turn。

### Phase 2：教练模式闭环

目标：优先打通训练价值。

- 支持主问题、首次回答、诊断、提示、同题重答、提升对比。
- 每个 topic 最多 2 次重答。
- 提示不给完整答案，只给结构和补充方向。

验收：

- 用户能完成一个 topic 的“首次回答 -> 提示 -> 重答 -> 对比反馈”。
- 报告中能展示 `initial_score / retry_score / score_delta`。

### Phase 3：严厉模式闭环

目标：实现技术面试压力测试。

- 主问题后最多 2 次追问。
- 追问聚焦职责、指标、异常、取舍、真实性。
- 不给提示，不允许重答。

验收：

- 回答空泛时能追问实现细节。
- 回答较好时能追问权衡或边界。
- 达到退出条件或最大 turn 后自动换 topic。

### Phase 4：跨 session topic 去重

目标：解决多轮重复偏高。

- 保存 topic 历史。
- 生成计划时读取最近 N 次面试主题。
- 低分 topic 进入明确标记的同题再练。

验收：

- 连续创建 3 次面试，核心 topic 不再机械重复。
- 若重复，必须是不同角度或复练任务。

### Phase 5：动态面试质量基准

目标：从“出题质量”升级到“过程质量”。

新增基准指标：

- 主问题清晰度。
- 追问命中率。
- 教练提示有效性。
- 重答提升合理性。
- 严厉追问压强。
- topic 多样性。
- 分类准确率。
- 生成耗时。

每道基准题准备 4 类回答：

- 强回答。
- 一般回答。
- 空泛回答。
- 跑偏回答。

验证排序：

```text
强回答 > 一般回答 > 空泛回答 > 跑偏回答
```

## 12. 非目标

第一版不做：

- 实时语音打断。
- 完全自由聊天。
- 多人面试。
- 企业招聘官视角。
- 大规模题库运营后台。
- 中途任意切换模式。

模式切换规则：

- 创建面试前选择 `strict` 或 `coach`。
- 中途只能在 topic 结束后切换，第一版可以先不支持中途切换。

## 13. 风险与挑战

### 13.1 伪动态风险

如果只是把静态题拆成多段文本，本质仍是题库生成器。

应对：必须引入 `signals -> policy -> decision`。

### 13.2 评分漂移风险

严厉模式和教练模式如果使用不同评分标准，趋势图会失真。

应对：统一 `ability_score`，模式只影响交互策略。

### 13.3 教练代答风险

教练模式如果直接给完整答案，用户会复制答案而不是训练表达。

应对：提示只给结构、方向和缺口，不给完整代答。

### 13.4 追问失控风险

LLM 容易越问越散。

应对：topic 有 `followup_goals`、`exit_criteria`、`max_turns`。

### 13.5 数据复杂度上升

新增 topic/turn/decision 会让模型复杂度上升。

应对：先用 DTO 和 JSON 字段承载，等流程稳定后再拆更细表结构。

## 14. 建议优先级

近期优先：

1. 设计并落地 `InterviewTopic`、`InterviewTurn`、`InterviewDecision` DTO。
2. 把现有题目生成改成 `main_question + followup_goals + evidence_snippet`。
3. 先做教练模式的同题重答闭环。
4. 再做严厉模式的连续追问。
5. 最后补跨 session topic 去重和动态质量基准。

暂缓：

- 复杂前端动效。
- 实时语音。
- 企业端。
- 组织/班级能力。

## 15. 仍需讨论的问题

1. 第一版 topic 数固定为 4 还是 5？
2. 严厉模式是否允许用户跳过问题？
3. 教练模式重答最多 2 次是否合适？
4. `system_design` 是否进入最终总分，还是单独展示？
5. 历史 topic 去重按最近 2 次、最近 7 天，还是两者结合？
6. 动态面试报告按 topic 汇总，还是兼容旧报告按 question 汇总？
