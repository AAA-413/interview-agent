# 动态面试生成耗时与等待体验优化方案

文档日期：2026-05-28

## 1. 背景

当前模拟面试质量基准中，8 道题生成耗时约：

```text
22.2s
38.1s
48.0s
```

这对正式产品体验偏慢。

根因不是单纯模型慢，而是当前把“一整场面试的生成成本”集中压在创建会话这一步：

```text
创建会话 -> 一次性生成所有题目 -> 用户等待 -> 进入面试
```

动态面试官应改为：

```text
创建会话 -> 生成计划和第一题 -> 用户开始答题
答题后 -> 按需生成追问、提示或下一题
```

核心目标：

```text
不要一次生成完整面试，而是让用户尽快进入第一轮互动。
```

## 2. 性能目标

第一版目标：

```text
创建动态面试：15s 内返回第一题
提交回答后：10s 内返回评分和下一步
```

第二版目标：

```text
创建 session 立即返回 PLANNING
3-8s 内展示第一题
后续每轮 1-5s 内返回下一步
```

产品体验目标：

- 用户不再长时间面对空转圈。
- 用户能看到明确的生成阶段。
- 即使 LLM 部分失败，也不丢答案、不阻断流程。

## 3. 生成策略

### 3.1 不一次性生成完整面试

创建会话时只生成：

```text
InterviewPlan
4-5 个 topic
第 1 个 main_question
```

用户回答后再按需生成：

```text
当前 topic 的追问
教练提示
同题重答问题
下一 topic 的主问题
```

好处：

- 首屏更快。
- 用户中途退出时减少浪费。
- 追问能真正基于用户回答动态生成。
- 主问题更清晰，不需要一道题塞多个子问题。

### 3.2 主问题轻，追问深

主问题只承担一个核心目标：

```text
请先讲清整体链路和个人职责。
```

细节、指标、异常、权衡进入后续动态追问。

## 4. 前端等待体验

等待不能只是空转圈。

建议展示阶段：

```text
正在分析简历项目
正在匹配 JD 重点
正在选择面试主题
正在准备第一题
```

如果进入 `PLANNING` 状态：

```text
面试计划生成中，请稍候...
```

如果失败：

```text
面试计划生成失败，可以重试；已保存你的会话配置。
```

第一版可以使用轮询，不必立刻引入 SSE。

## 5. 缓存设计

建议分三层缓存。

### 5.1 Resume Profile Cache

简历上传或分析后生成并缓存：

```text
project_cards
skill_graph
risk_points
evidence_snippets
topic_candidates
```

作用：

- 多次面试复用。
- 减少创建面试时对简历全文的重复分析。
- 为项目题证据绑定提供稳定输入。

缓存 key：

```text
resume_id + resume_updated_at/version
```

### 5.2 JD Strategy Cache

JD 结构化后缓存：

```text
structured_jd
quality_score
role_domain
seniority
topic_weights
question_type_mix
```

缓存 key：

```text
user_id + jd_hash + target_role + skill_id
```

作用：

- 同一个 JD 多次训练策略稳定。
- 避免重复解析 JD。
- 让 topic 权重可解释。

### 5.3 Topic Plan Cache

每场面试生成后保存：

```text
session_id
topics
current_topic_id
current_turn_id
topic_status
turn_status
```

作用：

- 支持恢复面试进度。
- 支持前端轮询。
- 支持失败后重试。

## 6. 状态设计

动态面试 session 状态：

```text
PLANNING
INTERVIEWING
COMPLETED
FAILED
ABANDONED
```

创建会话响应可以有两种：

### 6.1 同步返回第一题

适用于第一版：

```json
{
  "session_id": "abc",
  "status": "INTERVIEWING",
  "current_turn": {
    "turn_id": 1,
    "question": "..."
  }
}
```

### 6.2 异步返回 PLANNING

适用于第二版：

```json
{
  "session_id": "abc",
  "status": "PLANNING",
  "message": "正在生成面试计划"
}
```

前端轮询：

```http
GET /api/interview/dynamic-sessions/{session_id}
```

直到：

```text
INTERVIEWING + current_turn
```

## 7. API 草案

### 7.1 创建动态面试

```http
POST /api/interview/dynamic-sessions
```

响应一：已生成第一题。

```json
{
  "session_id": "abc",
  "status": "INTERVIEWING",
  "current_topic": {},
  "current_turn": {}
}
```

响应二：仍在生成。

```json
{
  "session_id": "abc",
  "status": "PLANNING",
  "current_topic": null,
  "current_turn": null
}
```

### 7.2 获取会话状态

```http
GET /api/interview/dynamic-sessions/{session_id}
```

返回：

```json
{
  "session_id": "abc",
  "status": "INTERVIEWING",
  "topics": [],
  "current_topic": {},
  "current_turn": {}
}
```

### 7.3 提交回答

```http
POST /api/interview/dynamic-sessions/{session_id}/turns/{turn_id}/answer
```

响应：

```json
{
  "evaluation": {},
  "decision": {},
  "next_turn": {},
  "status": "INTERVIEWING"
}
```

## 8. 超时与失败兜底

动态面试官最怕用户答完后系统卡死。

必须设计兜底：

### 8.1 评分成功，追问失败

策略：

```text
保存评分和用户回答
生成规则兜底追问，或进入下一 topic
记录 decision fallback
```

### 8.2 评分失败

策略：

```text
保存用户回答
返回“评分暂时失败，可重试”
不丢答案
允许重新触发评分
```

### 8.3 教练提示失败

策略：

```text
返回基础规则提示
例如：请按 背景-方案-个人职责-指标-复盘 重新组织
```

### 8.4 Plan 生成失败

策略：

```text
session.status = FAILED
保留用户选择的 resume_id、JD、mode
允许一键重试
```

## 9. 成本与延迟观测

动态面试每个 turn 都可能触发 LLM，因此必须记录成本和延迟。

建议记录：

```text
session_id
topic_id
turn_id
operation_type
llm_provider
model_name
prompt_tokens
completion_tokens
latency_ms
cost_estimate
success
error_type
created_at
```

operation_type 示例：

```text
JD_PARSE
TOPIC_PLAN
MAIN_QUESTION_GENERATE
ANSWER_EVALUATE
FOLLOWUP_GENERATE
COACH_HINT_GENERATE
REPORT_GENERATE
```

用途：

- 估算单场动态面试成本。
- 找出最慢环节。
- 比较不同模型和策略。
- 做超时和重试优化。

## 10. 第一版实施建议

第一版不要过度复杂，先做“可感知快”：

```text
创建面试:
  同步生成 plan + 第一题
  目标 15s 内

提交回答:
  同步评分 + 决策下一步
  目标 10s 内

缓存:
  Resume Profile Cache
  JD Strategy Cache
```

如果超过目标时间：

```text
创建面试返回 PLANNING
前端轮询状态
```

## 11. 第二版优化

第二版做异步化：

- 创建 session 立即返回。
- 后台生成 plan。
- 前端轮询第一题。
- 对 Top 3 风险 topic 异步预取讲解资料。
- 对下一 topic 的主问题做预生成。

注意：

预生成只能用于主问题，不应该预生成完整追问，因为追问依赖用户回答。

## 12. 质量基准

生成体验需要单独纳入质量基准：

- 创建面试到第一题耗时。
- 提交回答到下一步耗时。
- 失败时是否保留用户回答。
- plan 失败是否可重试。
- 是否出现长时间无反馈。
- LLM 成本是否可观测。
- 异步状态是否准确。

## 13. 最终原则

动态面试官的性能目标不是：

```text
一次生成所有题更快
```

而是：

```text
用户尽快进入第一轮互动，并且每次回答后都有稳定反馈。
```
