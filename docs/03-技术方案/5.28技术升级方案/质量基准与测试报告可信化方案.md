# 质量基准与测试报告可信化方案

文档日期：2026-05-28

## 1. 核心目标

当前测试如果只证明：

```text
接口通了
页面能显示
LLM 返回了内容
```

只能说明系统“能跑”，不能说明系统“可信”。

可信质量基准要回答：

```text
系统有没有稳定地产生正确行为？
改动之后有没有真的变好？
哪些地方仍然不可信？
```

因此需要将质量验证拆成多条可度量、可回归、可对比的质量线。

## 2. 总体原则

1. 固定样本，不靠临时手感判断。
2. 固定期望，不只看 LLM 输出是否流畅。
3. 自动指标和人工抽检结合。
4. 每次重要改动都和上一个 baseline 对比。
5. 面试质量和 RAG 质量分开评估。
6. LLM 可以辅助评估，但不能完全自证。

## 3. 五条质量线

### 3.1 出题质量基准

验证系统是否问得对。

固定样本建议：

```text
简历 A：AI Agent / RAG
简历 B：Java 后端 / Redis / MySQL
简历 C：前端 / React / 性能优化
简历 D：Python 后端 / FastAPI
简历 E：LLM 微调 / LoRA / DPO
```

每份简历配一个固定 JD。

指标：

| 指标 | 含义 |
| --- | --- |
| `jd_alignment_score` | 题目是否贴合 JD |
| `resume_grounding_score` | 项目题是否基于简历证据 |
| `question_density_score` | 题目是否过密 |
| `topic_diversity_score` | topic 是否足够多样 |
| `question_type_accuracy` | project/knowledge/system_design 是否分类正确 |
| `unsupported_claim_rate` | 项目题中无证据断言比例 |
| `generation_latency` | 生成耗时 |

重点：

`unsupported_claim_rate` 是核心指标。项目题不能把简历或 JD 没有的内容写成候选人已经做过。

### 3.2 追问质量基准

验证系统是否真的根据用户回答动态追问。

每个主问题准备 4 类回答：

```text
强回答：链路、职责、指标、权衡都有
普通回答：讲了链路，但缺指标
空泛回答：只讲概念，没有实现
跑偏回答：答非所问
```

期望行为：

| 回答类型 | 期望决策 |
| --- | --- |
| 强回答 | 追问边界/权衡，或进入下一 topic |
| 普通回答 | 追问缺失指标或实现细节 |
| 空泛回答 | 追问个人职责、实现细节或降难度 |
| 跑偏回答 | 拉回问题、重新聚焦或换题 |

指标：

| 指标 | 含义 |
| --- | --- |
| `followup_target_accuracy` | 追问是否命中真实缺口 |
| `decision_action_accuracy` | follow_up/coach_retry/next_topic/end 是否合理 |
| `followup_relevance` | 追问是否和当前 topic 相关 |
| `unnecessary_followup_rate` | 强回答时是否还无意义追问 |
| `off_topic_followup_rate` | 追问跑题比例 |

### 3.3 评分质量基准

验证评分是否稳定、公平、可解释。

同题四类回答的期望排序：

```text
强回答 > 普通回答 > 空泛回答 > 跑偏回答
```

建议分数区间：

| 回答类型 | 期望分数 |
| --- | --- |
| 强回答 | 80-95 |
| 普通回答 | 60-80 |
| 空泛回答 | 35-60 |
| 跑偏回答 | 0-40 |

指标：

| 指标 | 含义 |
| --- | --- |
| `ranking_accuracy` | 强弱回答排序是否正确 |
| `score_band_accuracy` | 分数是否落在合理区间 |
| `explanation_consistency` | 评分理由是否和分数一致 |
| `mode_score_stability` | 严厉/教练模式下能力分是否稳定 |
| `dimension_score_consistency` | 维度分是否和总分一致 |

约束：

严厉模式和教练模式可以反馈风格不同，但同一回答的 `ability_score` 不应明显漂移。第一版可要求差异不超过 5 分。

### 3.4 教练提升基准

验证教练模式是否真的带来训练价值。

样本：

```text
首次回答：普通/空泛
教练提示：系统生成
重答回答：人工准备的改进版
```

期望：

```text
retry_score > initial_score
反馈能准确指出提升来源
hint 不直接给完整答案
```

指标：

| 指标 | 含义 |
| --- | --- |
| `retry_delta_correctness` | 重答分是否合理提升 |
| `hint_actionability` | 提示是否可执行 |
| `hint_no_answer_leakage` | 提示是否没有直接泄露完整答案 |
| `improvement_attribution_accuracy` | 是否准确说明提升来自哪里 |
| `remaining_gap_accuracy` | 是否指出重答后仍存在的问题 |

重点：

教练模式不能变成代答。提示应给结构、方向和缺口，不直接输出完整标准答案。

### 3.5 RAG 讲解质量基准

RAG 质量单独评估，不混进模拟面试评分。

指标：

| 指标 | 含义 |
| --- | --- |
| `retrieval_hit_rate` | 是否召回正确片段 |
| `citation_precision` | 引用片段是否真的相关 |
| `answer_faithfulness` | 回答是否忠实于引用 |
| `no_hit_honesty` | 找不到资料时是否诚实标记 |
| `fallback_label_accuracy` | personal/system/no-hit 来源是否标对 |
| `kb_isolation` | 多用户知识库是否隔离 |

重点：

- 无高置信资料时应返回 `NO_KB_HIT`。
- 不允许强行引用低相关片段。
- 不允许用 RAG 检索结果直接影响面试评分。

## 4. 测试样本设计

第一版建议小而硬：

```text
5 份简历
每份 1 个固定 JD
每份生成 1 场动态面试
每场选 2 个 topic 做追问测试
每个 topic 配 4 类回答
```

覆盖方向：

| 样本 | 覆盖方向 |
| --- | --- |
| A | AI Agent、RAG、MCP |
| B | Java 后端、Redis、MySQL、Spring |
| C | 前端、React/Vue、性能优化 |
| D | Python 后端、FastAPI、异步任务 |
| E | LLM 微调、LoRA、DPO、评估 |

每个样本应保存：

```text
resume_text
jd_text
expected_topic_keys
forbidden_claims
expected_question_type_mix
sample_answers
expected_score_bands
expected_followup_targets
```

## 5. 自动指标层

自动测试应输出机器可读结果：

```json
{
  "run_id": "2026-05-28",
  "sample_count": 5,
  "question_quality": {},
  "followup_quality": {},
  "scoring_quality": {},
  "coach_quality": {},
  "rag_quality": {},
  "latency": {},
  "failures": []
}
```

自动指标包括：

- 测试样本数。
- 通过率。
- 平均耗时。
- 失败用例。
- 分数排序准确率。
- 无证据断言率。
- 追问命中率。
- 教练提示可执行率。
- RAG 无命中诚实率。

## 6. 人工抽检层

LLM 评估不能完全自证。

每次大改 prompt、评分规则、Topic Registry 或 RAG 策略时，至少抽检：

```text
5 个出题样本
5 个追问样本
5 个评分样本
3 个 RAG 讲解样本
```

人工只判断关键项：

```text
是否贴合简历
是否问歪
评分是否离谱
提示是否泄露答案
讲解是否瞎引用
```

人工抽检结果需要进入报告：

```text
manual_review_pass_rate
manual_findings
blocking_issues
```

## 7. 版本对比层

每次重要改动都要和上一版 baseline 对比：

```text
当前版本 vs 上一版本

出题 JD 贴合度：+4%
无证据项目断言率：-2%
生成耗时：-8s
评分排序准确率：持平
RAG no-hit honesty：+12%
```

没有版本对比，就无法判断改动是变好还是变坏。

建议保存：

```text
tests/quality_baselines/{date_or_version}/results.json
tests/quality_baselines/{date_or_version}/report.md
```

## 8. 报告格式

建议报告结构：

```text
# 质量基准报告 - 2026-05-28

## 总体结论

当前版本：可演示 / 可内测 / 不建议发布
最大风险：评分排序不稳定、项目题偶发无证据扩写

## 核心指标

- 出题 JD 贴合度：87%
- 简历证据命中率：82%
- 无证据项目断言率：6%
- 追问命中率：74%
- 评分排序准确率：88%
- 教练提示可执行率：80%
- RAG 无命中诚实率：95%

## 阻塞问题

- Java 简历 Redis topic 被误归到 Agent memory
- 教练提示有 2 例泄露完整答案
- RAG 无命中时仍引用低相关片段

## 建议动作

- 收紧 Topic Registry pack 选择
- 增加 hint no-answer-leakage 规则
- 设置 RAG citation threshold
```

## 9. 发布门槛建议

### 9.1 可演示

```text
核心接口可用
出题贴合度 >= 75%
无严重权限/数据隔离问题
```

### 9.2 可内测

```text
出题 JD 贴合度 >= 80%
简历 grounding >= 80%
评分排序准确率 >= 80%
RAG no-hit honesty >= 90%
无 P0/P1 阻塞问题
```

### 9.3 可公开试用

```text
出题 JD 贴合度 >= 85%
简历 grounding >= 85%
评分排序准确率 >= 88%
追问命中率 >= 80%
教练提示可执行率 >= 85%
RAG no-hit honesty >= 95%
生成第一题 P90 <= 15s
无 P0/P1 阻塞问题
```

## 10. CI 与手动执行边界

不建议一开始把所有 LLM 质量基准都放进 CI。

建议：

### CI 必跑

- DTO/schema 单测。
- Topic Registry 映射单测。
- 分数聚合规则单测。
- RAG fallback 规则单测。
- 不依赖外部 LLM 的确定性测试。

### 手动或定时跑

- LLM 出题质量基准。
- LLM 追问质量基准。
- LLM 评分质量基准。
- RAG 真实检索质量基准。
- 版本对比报告。

### 发布前必跑

- 全量质量基准。
- 人工抽检。
- 版本对比。

## 11. 实施阶段

### Phase 1：样本集和报告模板

- 固化 5 份代表性简历。
- 固化 5 个 JD。
- 为每个 topic 准备 4 类回答。
- 建立 report.md 模板。

### Phase 2：确定性自动指标

- 实现 topic_key 命中检查。
- 实现 question_type 检查。
- 实现 unsupported_claim 检查。
- 实现评分排序检查。
- 实现 RAG no-hit 标记检查。

### Phase 3：LLM 质量评估辅助

- 使用 LLM 辅助评估追问是否命中缺口。
- 使用 LLM 辅助评估教练提示是否可执行。
- 使用 LLM 辅助评估讲解是否忠实引用。

### Phase 4：人工抽检和版本对比

- 每次大改生成报告。
- 抽检关键样本。
- 将当前版本与上一个 baseline 比较。
