# 动态面试报告与训练任务生成规则

文档日期：2026-05-28

## 1. 目标

动态面试报告不是“分数 + AI 评语”的展示页，而是一次面试后的训练决策页。

它要优先回答三个问题：

```text
1. 我现在准备度是多少？
2. 我最危险的 3 个问题是什么？
3. 我明天应该练什么？
```

报告和训练任务必须基于结构化数据生成，LLM 只负责解释和润色，不负责随意决定优先级。

## 2. 报告首页结构

第一屏建议展示：

- 综合准备度。
- 题型表现。
- 能力表现。
- 高风险点 Top 3。
- 明日 3 件事。

示例：

```text
综合准备度：76

题型表现：
- 项目题：82
- 知识题：70
- 系统设计：68

高风险点：
- RAG 指标口径说不清，30% 提升无法自证
- 多 Agent 执行链路能讲流程，但异常恢复细节弱
- 系统设计题能提出方案，但缺少容量、延迟和成本权衡

明日 3 件事：
- 补齐 RAG 30% 提升的证明口径
- 做一次 Cross-Encoder 延迟优化系统设计题
- 重写智能下载项目 2 分钟表达版本
```

## 3. 分数结构

### 3.1 综合准备度

产品文案建议使用“综合准备度”，不要叫“面试通过率”。

默认权重：

```text
综合准备度 =
  项目表达与真实性 * 40%
+ 技术基础 * 25%
+ 系统设计/迁移能力 * 20%
+ 表达结构与沟通 * 15%
```

注意：

- 综合准备度是训练参考，不是招聘决策。
- 如果本场没有覆盖某一类题型，应按实际覆盖维度重新归一化。
- 不要把未覆盖维度按 0 分计算。

### 3.2 题型表现

按 `question_type` 汇总：

```text
project_score
knowledge_score
system_design_score
```

用途：

- 判断用户在哪类题上短板明显。
- 生成报告分区。
- 辅助训练任务类型选择。

### 3.3 能力表现

能力维度跨题型汇总：

```text
authenticity
technical_depth
knowledge_accuracy
system_thinking
communication_structure
```

说明：

- `authenticity`：项目真实性、个人职责、是否经得起追问。
- `technical_depth`：实现细节、边界条件、异常处理和取舍。
- `knowledge_accuracy`：基础知识准确性。
- `system_thinking`：系统设计、扩展性、稳定性、成本、延迟。
- `communication_structure`：表达结构、重点、逻辑顺序。

训练计划应优先基于能力维度，而不是只看总分。

## 4. Topic 级报告

动态面试报告应按 topic 汇总，而不是按题号汇总。

每个 topic 展示：

```text
topic_title
topic_key
question_type
evidence_snippet
main_question
turn_summary
initial_score
final_score
best_score
score_delta
strengths
risks
next_training_action
```

示例：

```text
RAG 多通道检索

证据：简历中提到向量相似度 + BM25，多通道召回，Cross-Encoder 重排序。

首次回答：62
重答后：78
提升：+16

主要问题：
- 说到了 30% 提升，但缺少 baseline、测试集和指标口径。
- 能讲链路，但没有解释召回合并和去重策略。

下一步：
- 补齐 RAG 指标证明口径。
```

## 5. 严厉模式与教练模式报告差异

### 5.1 严厉模式

严厉模式重点展示抗压漏洞：

```text
你目前经不起追问的点是什么？
哪些项目细节不可信？
哪些指标说不清？
哪些技术点只会概念不会落地？
```

报告字段重点：

- `pressure_risks`
- `authenticity_risks`
- `metric_gaps`
- `implementation_gaps`
- `followup_failures`

### 5.2 教练模式

教练模式重点展示训练收益：

```text
第一次回答缺什么？
提示后补上了什么？
同题重答提升多少？
下次应该练哪种表达结构？
```

报告字段重点：

- `initial_score`
- `retry_score`
- `score_delta`
- `improved_dimensions`
- `remaining_gaps`
- `next_retry_task`

注意：

教练提示后的重答分不能直接污染“裸面水平”趋势。

趋势至少分三条：

```text
首次回答分：真实水平
重答后分：训练后表现
提升幅度：学习收益
```

## 6. 训练任务来源

训练任务来源必须结构化：

```text
topic_summary
turn_evaluation
coach_retry_delta
resume_analysis
jd_match
history_weakness
```

说明：

- `topic_summary`：topic 最终表现。
- `turn_evaluation`：具体回答暴露的问题。
- `coach_retry_delta`：提示后是否提升。
- `resume_analysis`：简历本身的问题。
- `jd_match`：topic 对 JD 的重要性。
- `history_weakness`：历史是否反复薄弱。

## 7. 任务优先级规则

训练任务不要让 LLM 纯生成，先由规则排序。

建议公式：

```text
priority_score =
  weakness_severity * 0.30
+ jd_relevance * 0.25
+ resume_core_project * 0.20
+ repeat_failure * 0.15
+ low_improvement * 0.10
```

字段说明：

- `weakness_severity`：这次答得差不差。
- `jd_relevance`：JD 是否重视这个 topic。
- `resume_core_project`：是否是简历核心项目。
- `repeat_failure`：历史是否反复失败。
- `low_improvement`：教练提示后是否仍没有明显提升。

不要简单按最低分排序。

一个边缘知识点 50 分，不一定比核心项目 70 分更急。

## 8. 训练任务类型

第一版固定任务类型：

| task_type | 场景 | 入口 |
| --- | --- | --- |
| `RETRY_TOPIC` | 同 topic 重练 | 动态面试同题再练 |
| `PROJECT_PROOF` | 项目指标、证据说不清 | 项目证明口径练习 |
| `FIX_RESUME_EVIDENCE` | 简历证据不足或表达错误 | 简历优化 |
| `KNOWLEDGE_DRILL` | 知识点错误或空泛 | 知识题训练 |
| `SYSTEM_DESIGN_DRILL` | 系统设计权衡不足 | 系统设计题训练 |
| `EXPRESSION_REWRITE` | 表达结构差 | 表达重写练习 |

生成规则：

```text
project + 指标说不清 -> PROJECT_PROOF
project + 简历证据不完整 -> FIX_RESUME_EVIDENCE
knowledge + 概念错误 -> KNOWLEDGE_DRILL
system_design + 权衡不足 -> SYSTEM_DESIGN_DRILL
表达结构差 -> EXPRESSION_REWRITE
教练后仍低分 -> RETRY_TOPIC
```

## 9. 明日 3 件事

报告页默认不直接展示完整 7 天计划，而是优先展示“明日 3 件事”。

默认组合：

```text
1 个最高风险项目任务
1 个知识/系统设计补弱任务
1 个表达或简历修正任务
```

示例：

```text
1. 补齐 RAG 30% 提升的证明口径
   类型：PROJECT_PROOF
   动作：写清 baseline、指标、测试集、对比结果。

2. 做一次 Cross-Encoder 延迟优化系统设计题
   类型：SYSTEM_DESIGN_DRILL
   动作：从候选集大小、缓存、分层重排、降级策略四点回答。

3. 重写智能下载项目描述
   类型：EXPRESSION_REWRITE
   动作：按 背景-方案-个人职责-指标-复盘 改写 2 分钟版本。
```

用户可进一步展开：

```text
3 天训练计划
7 天训练计划
```

## 10. LLM 的职责边界

LLM 不决定“练什么优先”。

LLM 负责：

- 把规则选出的任务写成用户能理解的话。
- 将反馈压缩成清晰行动。
- 生成适合练习的任务标题和说明。

LLM 输入示例：

```json
{
  "task_type": "PROJECT_PROOF",
  "topic_key": "rag_multi_channel_retrieval",
  "weakness": "指标口径不清",
  "evidence": "回答提到召回准确率提升 30%，但没有 baseline 和评估集",
  "action_constraints": ["必须包含 baseline", "必须包含指标", "必须包含测试数据来源"],
  "max_words": 80
}
```

LLM 输出示例：

```text
补齐 RAG 召回准确率提升 30% 的证明口径：写出 baseline、评估指标和测试集来源，并用 3 句话说明提升如何测得。
```

## 11. 任务状态

第一版任务状态：

```text
TODO
DONE
SKIPPED
```

后续可扩展：

```text
RETRY_SCHEDULED
```

任务应绑定：

```text
user_id
session_id
topic_key
evidence_hash
weakness_type
task_type
priority_score
status
```

同题再练不应只绑定原题文本，而应绑定：

```text
topic_key + evidence_hash + weakness_type
```

这样可以换问法，但训练同一个短板。

报告 JSON：

```json

  "type_scores": {
    "project": 82,
    "knowledge": 70,
    "system_design": 68
  },
  "ability_scores": {
    "authenticity": 85,
    "technical_depth": 78,

  "top_risks": [],
  "topic_summaries": [],
  "tomorrow_tasks": [],

  "resume_fix_suggestions": []
}
```

训练任务 JSON：

```json
{
  "task_type": "PROJECT_PROOF",
  "topic_key": "rag_multi_channel_retrieval",
  "evidence_hash": "abc",
  "weakness_type": "metric_validation",

  "status": "TODO"
}
```

## 13. 质量基准

报告和训练任务需要单独评估：

- 高风险点是否来自真实回答证据。
- 明日 3 件事是否覆盖最高优先级短板。
- 任务是否可执行，而不是泛泛建议。
- 教练模式是否展示首次回答、重答和提升来源。
- 严厉模式是否展示抗压漏洞。
- 训练计划是否没有被低优先级知识点干扰。
