# 上传去重修复说明

修复日期：2026-05-28

## 1. 问题现象

使用新账号上传一份已经被其他账号上传过的 PDF 简历时，接口返回：

```text
简历不存在或已被删除
```

这不是文件解析失败，而是上传去重和用户权限过滤之间的冲突。

## 2. 根因

原逻辑按全局 `file_hash` 去重：

```text
find_by_file_hash(file_hash)
```

如果其他用户已经上传过同一份文件，上传服务会直接返回那条已有简历记录。但后续详情查询会按当前用户过滤：

```text
get_resume_detail(resume_id, current_user_id)
```

于是出现：

```text
上传阶段命中其他用户的 resume
  -> 详情阶段当前用户无权访问
  -> 返回“简历不存在或已被删除”
```

数据库层还有一个更深的问题：`resumes.file_hash` 被定义为全局唯一，天然不允许不同用户保存同一份简历记录。

## 3. 修复方案

本次采用“用户级去重”：

- 同一用户重复上传同一文件：继续复用自己的简历记录。
- 不同用户上传同一文件：创建各自独立的简历记录。
- 文件存储层是否复用对象，后续可单独优化；当前优先保证权限边界正确。

## 4. 代码改动

### 4.1 模型约束

文件：

```text
app/modules/resume/models.py
```

调整：

- 移除 `file_hash` 全局唯一。
- 新增 `(user_id, file_hash)` 组合唯一索引。

### 4.2 查询逻辑

文件：

```text
app/modules/resume/persistence_service.py
```

调整：

- `find_by_file_hash` 支持传入 `user_id`。
- `exists_by_file_hash` 支持传入 `user_id`。

### 4.3 上传逻辑

文件：

```text
app/modules/resume/upload_service.py
```

调整：

上传去重改为：

```text
find_by_file_hash(file_hash, user_id=current_user_id)
```

只复用当前用户自己的历史简历。

### 4.4 数据库迁移

文件：

```text
alembic/versions/005_scope_resume_file_hash_by_user.py
```

迁移内容：

- 删除旧的全局 `file_hash` 唯一索引/约束。
- 新增 `idx_resume_user_file_hash` 组合唯一索引。

## 6. 本地数据库处理

本地执行 `alembic upgrade head` 时，因为当前数据库表结构已经存在，但 Alembic 版本表没有完整记录历史迁移，命令尝试从 `001` 重放，撞到已存在的 `user_id` 列。

因此本地仅手动执行了本次修复对应的安全 SQL：

```sql
DROP INDEX IF EXISTS idx_resume_hash;
ALTER TABLE resumes DROP CONSTRAINT IF EXISTS resumes_file_hash_key;
CREATE UNIQUE INDEX IF NOT EXISTS idx_resume_user_file_hash ON resumes (user_id, file_hash);
```

确认结果：

```text
idx_resume_user_file_hash CREATE UNIQUE INDEX idx_resume_user_file_hash ON public.resumes USING btree (user_id, file_hash)
```

## 7. 后续建议

1. 整理 Alembic 版本表和当前数据库结构的关系，避免后续迁移重放失败。
2. 如果要节省对象存储空间，可后续拆出文件对象表，让多用户 resume 记录引用同一个文件对象。
3. 对知识库上传也检查是否存在类似全局 `file_hash` 去重和用户隔离冲突。
